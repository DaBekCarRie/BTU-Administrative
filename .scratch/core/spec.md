# Spec: ระบบผู้สนใจ–ผู้เรียน รอบแรก

Status: ready-for-agent

ศัพท์ทั้งหมดในเอกสารนี้ใช้ตาม [CONTEXT.md](../../CONTEXT.md)
การตัดสินใจที่ย้อนกลับยากอยู่ใน [docs/adr/](../../docs/adr/)

## Problem Statement

ทีม LMS มหาวิทยาลัยกรุงเทพธนบุรี (เจ้าหน้าที่ 5 คน + หัวหน้าทีม 1 คน) ทำงานรับสมัคร
และติดตามนักศึกษาบน Google Sheets กับแชท LINE ปัญหาที่เจอทุกวัน:

- **ไม่รู้ว่าวันนี้ต้องโทรหาใคร** ชีทมี 3,180 ราย แต่บอกไม่ได้ว่าใครถึงคิว
- **ตามได้แค่ 6 ครั้ง** ช่องติดตามเป็นคอลัมน์ และมี 42 คนใช้ครบแล้ว
- **ข้อมูลเละเพราะพิมพ์มือ** คณะ 10 คณะกลายเป็น 64 ค่า · ชื่อเจ้าหน้าที่ 5 คนกลายเป็น 16 ค่า
  เพราะวรรณยุกต์ซ้ำที่มองด้วยตาไม่เห็น → สรุปยอดผิดทันที
- **สถานะปนกับวันที่** ช่อง "วันที่ให้โทร" กรอกไว้ 1,530 แถว แต่ 1,486 แถวไม่ใช่วันที่
- **ประวัติถูกเขียนทับ** พอสถานะเปลี่ยน ของเดิมหาย ตอบไม่ได้ว่าเทอมที่แล้วคนนี้อยู่สถานะอะไร
- **เอกสารส่วนบุคคลลอยอยู่ในแชท** สำเนาบัตรประชาชนถูกถ่ายรูปส่งเข้ากลุ่ม LINE
  ค้างในเครื่องทุกคนถาวร ตามลบไม่ได้ ไม่รู้ว่าใครเปิดดู
- **ถามซ้ำเรื่องเดิม** คำถาม "ค่าทำบัตรนักศึกษา 200 บาท หรือนักศึกษาใหม่ทำฟรี"
  ใช้เวลา 2 วันถามข้ามฝ่ายและได้คำตอบขัดกัน
- **รายชื่อศูนย์สอบพิเศษพิมพ์ใหม่ทั้งก้อน** 3 ครั้งใน 4 วัน เพราะมีคนเพิ่มและถอนชื่อ

## Solution

เว็บแอปภายในที่แทน Google Sheets สำหรับงานติดตามผู้สนใจจนถึงการเป็นผู้เรียน

หัวใจคือ **เก็บทุกอย่างเป็นเหตุการณ์ที่เพิ่มอย่างเดียว** แล้วคำนวณ `สถานะปัจจุบัน`
จากเหตุการณ์ ([ADR-0001](../../docs/adr/0001-hybrid-event-log.md)) ทำให้ประวัติไม่หาย
และย้อนดูได้ว่าเทอมไหนเกิดอะไร

หน้าแรกคือ **กระดานงานค้าง** ที่ตอบว่า "ตอนนี้ต้องทำอะไร" ไม่ใช่ตารางข้อมูลเปล่า ๆ
ทุกช่องประเภทเป็น dropdown จากข้อมูลหลัก ปิดปัญหาพิมพ์ผิดถาวร
เอกสารเก็บใน bucket ปิด เปิดดูผ่านลิงก์หมดอายุและบันทึก log ทุกครั้ง

## User Stories

### คิวโทรและการติดตาม

1. As a เจ้าหน้าที่, I want เปิดระบบแล้วเห็นทันทีว่าวันนี้ต้องโทรหาใครบ้าง, so that ไม่ต้องไล่หาเองในตาราง 3,180 แถว
2. As a เจ้าหน้าที่, I want เห็นว่าคนไหนเลยกำหนดนัดโทรมาแล้วกี่วัน, so that จัดลำดับคนที่ค้างนานที่สุดก่อนได้
3. As a เจ้าหน้าที่, I want เห็นผลการโทรครั้งล่าสุดย่อ ๆ ในแถวเดียวกับชื่อ, so that รู้บริบทก่อนกดโทรโดยไม่ต้องเปิดหน้าใหม่
4. As a เจ้าหน้าที่, I want กดเบอร์แล้วโทรออกจากมือถือได้เลย, so that ไม่ต้องพิมพ์เบอร์ซ้ำ
5. As a เจ้าหน้าที่, I want บันทึกผลการโทรจบได้ในไม่กี่แตะบนมือถือ, so that บันทึกได้ทันทีที่วางสาย
6. As a เจ้าหน้าที่, I want เลือกนัดโทรครั้งถัดไปแบบลัด (พรุ่งนี้ / 3 วัน / 1 สัปดาห์), so that ไม่ต้องเปิดปฏิทินเลือกวันทุกครั้ง
7. As a เจ้าหน้าที่, I want บันทึกการโทรย้อนหลังโดยระบุวันที่ที่โทรจริง, so that ข้อมูลตรงความจริงแม้บันทึกทีหลัง
8. As a เจ้าหน้าที่, I want เห็นประวัติการติดตามทั้งหมดของคนหนึ่งเรียงจากใหม่ไปเก่า, so that รู้ว่าคุยอะไรไปแล้วบ้าง
9. As a เจ้าหน้าที่, I want ตามคนเดิมได้ไม่จำกัดจำนวนครั้ง, so that ไม่ตันที่ครั้งที่ 6 เหมือนชีทเดิม
10. As a เจ้าหน้าที่, I want ปิดเคสพร้อมระบุเหตุผล (ไม่สนใจ / ติดต่อไม่ได้), so that คนที่ปิดแล้วไม่โผล่ในคิวอีก

### ค้นหาและรายชื่อ

11. As a เจ้าหน้าที่, I want ค้นหาด้วยชื่อไทยหรือชื่อ Facebook ภาษาอังกฤษก็ได้, so that หาเจอไม่ว่าคนนั้นให้ชื่อมาแบบไหน
12. As a เจ้าหน้าที่, I want ค้นเจอแม้พิมพ์ชื่อไม่ครบ, so that ไม่ต้องจำชื่อเต็ม
13. As a เจ้าหน้าที่, I want ค้นด้วยเบอร์โทรได้, so that หาคนเจอตอนมีสายเข้า
14. As a เจ้าหน้าที่, I want กรองรายชื่อตามสถานะ หลักสูตร ภาค และผู้ดูแล, so that โฟกัสกลุ่มที่กำลังทำอยู่
15. As a เจ้าหน้าที่, I want เห็นจำนวนผลลัพธ์และแบ่งหน้า, so that รู้ว่ากรองแล้วเหลือกี่คน
16. As a เจ้าหน้าที่, I want ส่งออกผลลัพธ์ที่กรองแล้วเป็น Excel, so that ส่งรายงานให้ผู้บริหารได้ และมีสำเนาไว้เผื่อระบบล่ม

### บันทึกและแก้ไขข้อมูล

17. As a เจ้าหน้าที่, I want เพิ่มผู้สนใจใหม่จากมือถือ, so that บันทึกได้ทันทีที่มีคนทักเข้ามา
18. As a เจ้าหน้าที่, I want เลือกคณะ สาขา ภาค วุฒิ จาก dropdown เท่านั้น, so that ไม่เกิดชื่อคณะเพี้ยน 64 แบบเหมือนเดิม
19. As a เจ้าหน้าที่, I want ระบบเตือนทันทีถ้ากรอกเบอร์ที่มีอยู่แล้ว พร้อมลิงก์ไปดูคนเดิม, so that ไม่สร้างข้อมูลซ้ำและไม่โทรซ้ำคนเดิม
20. As a เจ้าหน้าที่, I want แก้ไขข้อมูลติดต่อของคนที่มีอยู่แล้ว, so that ข้อมูลทันสมัยเมื่อเขาเปลี่ยนเบอร์
21. As a เจ้าหน้าที่, I want ระบบจัดรูปแบบเบอร์โทรให้เหมือนกันอัตโนมัติ, so that ค้นหาเจอไม่ว่าจะพิมพ์มาแบบไหน
22. As a หัวหน้าทีม, I want รวมสองรายการที่เป็นคนเดียวกันเข้าด้วยกัน, so that ประวัติไม่แตกเป็นสองเส้น
23. As a เจ้าหน้าที่, I want แก้รายการที่บันทึกผิดโดยที่ระบบเก็บร่องรอยว่ามีการแก้, so that ข้อมูลถูกต้องโดยไม่ทำลายประวัติ

### การสมัครและสถานะ

24. As a เจ้าหน้าที่, I want บันทึกว่าคนนี้ยื่นสมัครในปีการศึกษาและหลักสูตรไหน, so that แยกได้ว่าเป็นการสมัครรอบไหน
25. As a เจ้าหน้าที่, I want บันทึกการสมัครหลายครั้งให้คนคนเดียว, so that รองรับเคสลาออกแล้วสมัครใหม่
26. As a เจ้าหน้าที่, I want เห็นสถานะการติดตาม สถานะการเรียน และสถานะการเงิน แยกกันคนละช่อง, so that คนที่รักษาสภาพแต่ยังเรียนอยู่ไม่ถูกแสดงผิด
27. As a เจ้าหน้าที่, I want เห็นวันที่ยืนยันล่าสุดติดกับสถานะการเรียนและการเงินเสมอ, so that รู้ว่าข้อมูลนี้เก่าแค่ไหนก่อนจะเชื่อ
28. As a เจ้าหน้าที่, I want บันทึกว่าคนนี้ดรอปพร้อมเหตุผลและเครดิตค่าเทอมที่ค้างอยู่, so that ตอนเขากลับมาเรียนรู้ว่ามีเงินเหลือเท่าไหร่
29. As a เจ้าหน้าที่, I want บันทึกว่าคนนี้กลับมาเรียนแล้ว, so that สถานะการเรียนกลับเป็นปกติโดยประวัติดรอปยังอยู่
30. As a เจ้าหน้าที่, I want บันทึกการย้ายเทอม, so that รองรับคนที่ชำระไม่ทันแล้วเลื่อนไปเทอมถัดไป
31. As a เจ้าหน้าที่, I want บันทึกรหัสนักศึกษาเมื่อสำนักทะเบียนออกให้, so that อ้างอิงกับหน่วยงานอื่นได้
32. As a เจ้าหน้าที่, I want บันทึกการชำระเงินแต่ละงวดพร้อมแนบสลิป, so that ตรวจสอบย้อนหลังได้ว่าจ่ายอะไรไปแล้วบ้าง

### เอกสาร

33. As a เจ้าหน้าที่, I want อัปโหลดเอกสารประจำตัวของคนหนึ่ง (รูปถ่าย วุฒิ สำเนาบัตรประชาชน สำเนาทะเบียนบ้าน), so that ไม่ต้องส่งรูปในแชท
34. As a เจ้าหน้าที่, I want เห็นเช็กลิสต์ว่าเอกสารครบกี่จาก 4, so that รู้ว่ายังขาดอะไร
35. As a เจ้าหน้าที่, I want ทำเครื่องหมายว่าเอกสารผ่านหรือไม่ผ่านพร้อมเหตุผล, so that คนที่รับงานต่อรู้ว่าต้องขอใหม่เพราะอะไร
36. As a เจ้าหน้าที่, I want ใช้เอกสารประจำตัวเดิมกับการสมัครครั้งใหม่ได้, so that ไม่ต้องขอสำเนาบัตรประชาชนซ้ำจากคนเดิม
37. As a เจ้าหน้าที่, I want เห็นสำเนาบัตรประชาชนเป็นภาพเบลอจนกว่าจะกดเปิด, so that ไม่มีเลขบัตรคนอื่นค้างอยู่บนจอตอนมีคนเดินผ่าน
38. As a หัวหน้าทีม, I want ดูได้ว่าใครเปิดดูสำเนาบัตรประชาชนของใครเมื่อไหร่, so that ตอบได้ตาม PDPA ว่าข้อมูลถูกเข้าถึงโดยใครบ้าง
39. As a เจ้าหน้าที่, I want ระบบย่อรูปที่อัปโหลดจากมือถือให้อัตโนมัติ, so that ไม่เปลืองพื้นที่เก็บจนต้องจ่ายเพิ่ม
40. As a เจ้าหน้าที่, I want แนบใบเสร็จหรือแบบฟอร์มดรอปกับเหตุการณ์ที่มันเกิด, so that หาเอกสารเจอจากไทม์ไลน์

### คลังคำตอบ

41. As a เจ้าหน้าที่, I want ค้นคำถามที่เคยตอบไปแล้ว, so that ตอบผู้สนใจได้ทันทีโดยไม่ต้องถามใคร
42. As a เจ้าหน้าที่, I want เห็นว่าคำตอบนี้ยืนยันล่าสุดเมื่อไหร่และโดยใคร, so that รู้ว่ายังเชื่อได้อยู่ไหม
43. As a เจ้าหน้าที่, I want เห็นป้ายเตือนเมื่อคำตอบเก่าเกินกำหนด, so that ไม่เอาข้อมูลล้าสมัยไปบอกผู้สนใจ
44. As a เจ้าหน้าที่, I want รู้ว่าคำตอบไหนบอกผู้สนใจได้และคำตอบไหนใช้ภายในเท่านั้น, so that ไม่เผลอบอกกฎภายในออกไป
45. As a เจ้าหน้าที่, I want กดยืนยันว่าคำตอบนี้ยังถูกต้อง, so that วันที่ยืนยันล่าสุดอัปเดตโดยไม่ต้องพิมพ์ใหม่
46. As a เจ้าหน้าที่, I want เพิ่มคำถามใหม่พร้อมคำตอบและที่มา, so that ความรู้ไม่หายไปกับคนที่ถามมา

### ศูนย์สอบพิเศษ

47. As a เจ้าหน้าที่, I want บันทึกว่าใครขอสอบที่ศูนย์สอบพิเศษไหนในปีการศึกษาไหน, so that ไม่ต้องพิมพ์รายชื่อใหม่ทุกครั้งที่มีคนเพิ่ม
48. As a เจ้าหน้าที่, I want ถอนคำขอศูนย์สอบพิเศษออกโดยที่ยังเห็นว่าเคยขอ, so that รู้ประวัติว่าเปลี่ยนใจเมื่อไหร่
49. As a เจ้าหน้าที่, I want กดออกรายชื่อแยกตามศูนย์สอบเพื่อส่งต่อ, so that ส่งให้ผู้จัดสอบได้โดยไม่ต้องพิมพ์เอง
50. As a เจ้าหน้าที่, I want เห็นคำเตือนว่าต้องไปเช็กการลงทะเบียนสอบในระบบของมหาวิทยาลัยด้วย, so that ไม่ลืมกระทบยอดสองลิสต์

### กระดานงานและตัวเลขรวม

51. As a เจ้าหน้าที่, I want เห็นจำนวนงานค้างแยกประเภทบนหน้าแรก, so that รู้ภาพรวมก่อนเริ่มงาน
52. As a เจ้าหน้าที่, I want เห็นว่าใครจ่ายเงินแล้วแต่ยังไม่ได้รหัสนักศึกษา, so that ไม่มีใครตกหล่นระหว่างรอสำนักทะเบียน
53. As a เจ้าหน้าที่, I want เห็นว่าใครเอกสารยังไม่ครบ, so that ตามเก็บได้ก่อนถึงกำหนด
54. As a หัวหน้าทีม, I want เห็นตัวเลขรวมว่าเดือนนี้สมัครกี่คน เรียนอยู่กี่คน ดรอปกี่คน, so that รู้ภาพรวมโดยไม่ต้องทำ pivot เอง
55. As a หัวหน้าทีม, I want ตัวเลขบนกระดานไม่แยกเป็นรายบุคคลของเจ้าหน้าที่, so that ระบบไม่กลายเป็นเครื่องมือวัดผลคนโดยไม่ได้ตั้งใจ

### ระบบและข้อมูลเดิม

56. As a เจ้าหน้าที่, I want เข้าสู่ระบบด้วยอีเมลและรหัสผ่าน, so that ข้อมูลไม่เปิดให้คนนอก
57. As a เจ้าหน้าที่, I want เห็นและแก้ข้อมูลของเคสที่เพื่อนร่วมทีมดูแลได้, so that งานไม่ค้างเวลามีคนลา
58. As a หัวหน้าทีม, I want ดูได้ว่าใครแก้ข้อมูลอะไรเมื่อไหร่, so that ตามได้เวลาข้อมูลผิด
59. As a เจ้าหน้าที่, I want ข้อมูลเดิม 3,180 รายอยู่ในระบบตั้งแต่วันแรก, so that ไม่ต้องสลับไปเปิดชีทเก่า
60. As a หัวหน้าทีม, I want เห็นรายงานว่าการนำเข้าข้อมูลแปลงอะไรไปบ้างและแถวไหนแปลงไม่ได้, so that ตรวจก่อนยิงเข้าระบบจริง

## Implementation Decisions

### โครงข้อมูล

ตามหลักลูกผสม ([ADR-0001](../../docs/adr/0001-hybrid-event-log.md)) —
`เหตุการณ์` เป็นแหล่งความจริง `คน` เก็บ `สถานะปัจจุบัน` ที่คำนวณไว้แล้ว

| ตาราง | บทบาท |
|---|---|
| `faculties` / `programs` | ข้อมูลหลักคณะและสาขา เป็น FK ทุกที่ ห้ามพิมพ์อิสระ |
| `staff` | เจ้าหน้าที่ ผูกกับ `auth.users` มี role `staff` หรือ `admin` |
| `people` | คน 1 แถว — ข้อมูลติดต่อ + `สถานะปัจจุบัน` 3 มิติ + วันที่ยืนยันล่าสุดของแต่ละมิติ |
| `events` | เหตุการณ์ เพิ่มอย่างเดียว |
| `applications` | การสมัคร — คนเดียวมีได้หลายแถว |
| `documents` | เอกสารประจำตัว ผูกกับ `people` + บันทึกว่าใช้กับการสมัครไหน |
| `document_access_log` | ใครเปิดดูเอกสารอ่อนไหวเมื่อไหร่ |
| `exam_center_requests` | คำขอศูนย์สอบพิเศษ |
| `answers` | คลังคำตอบ + ป้ายการเปิดเผย + ยืนยันล่าสุดโดยใคร |

### เหตุการณ์ 15 ชนิด

```
ติดตาม   ติดต่อเข้ามา · โทรตาม · ปิดเคส
สมัคร    ยื่นสมัคร · ส่งเอกสาร · ตรวจเอกสาร · ชำระเงิน · ได้รหัสนักศึกษา
เรียน    ย้ายเทอม · ดรอป · กลับมาเรียน · ลาออก
สอบ      ขอศูนย์สอบพิเศษ · ถอนคำขอศูนย์สอบ
ข้อมูล   แก้ไขข้อมูล
```

`แก้ไขข้อมูล` ครอบคลุมการแก้ข้อมูลติดต่อและข้อมูลประจำตัว — **ห้าม `UPDATE` ตาราง `คน`
ตรง ๆ** เพราะจะทำให้ "ใครแก้ เมื่อไหร่" หายไป และขัดหลักแหล่งความจริงเดียวใน ADR-0001

ทุกเหตุการณ์เก็บ: คนที่เกี่ยวข้อง · ชนิด · เวลาที่เกิดจริง · เวลาที่บันทึก · ผู้บันทึก
· ข้อมูลเพิ่มเติมตามชนิด (jsonb)

เพิ่มชนิดใหม่ทีหลังได้ถูก เพราะเป็นแค่ค่า enum ใหม่ ไม่ต้องย้ายข้อมูล
เหตุการณ์เรื่อง กยศ. ยังไม่ทำในรอบนี้ เพราะข้อมูลเดิมกรอกไว้แค่ 14%

### สถานะ 3 มิติ

แยกกัน ห้ามยุบ ([ADR-0002](../../docs/adr/0002-three-status-dimensions.md))

| มิติ | ค่า | เจ้าของความจริง |
|---|---|---|
| การติดตาม | ใหม่ · กำลังติดตาม · นัดโทรแล้ว · สนใจสมัคร · สมัครแล้ว · ไม่สนใจ · ติดต่อไม่ได้ | ทีม |
| การเรียน | ยังไม่เริ่ม · เรียนอยู่ · ดรอป · ลาออก · จบแล้ว | สำนักทะเบียน |
| การเงิน | ยังไม่ชำระ · ผ่อนอยู่ · รักษาสภาพ · ชำระครบ | ฝ่ายการเงิน |

สองมิติหลังเป็นสำเนา ([ADR-0003](../../docs/adr/0003-not-the-source-of-truth.md)) —
**ทุกที่ที่แสดงต้องมีวันที่ยืนยันล่าสุดติดกับค่าเสมอ** ไม่ใช่ทางเลือกด้านดีไซน์
แต่เป็นสิ่งที่กันไม่ให้ทีมเชื่อข้อมูลที่อาจเก่าเป็นปี

### โมดูลโดเมน

ทุกการเขียนที่แตะ `คน` หรือ `เหตุการณ์` ผ่านโมดูลเดียว ซึ่งเปิดสองอย่าง:

- ฟังก์ชันบริสุทธิ์ที่รับ `สถานะปัจจุบัน` กับ `เหตุการณ์` แล้วคืนสถานะใหม่ ไม่แตะ I/O
- ฟังก์ชันบันทึกที่เขียน `events` และอัปเดต `people` ในทรานแซกชันเดียว
  โดยเรียกฟังก์ชันบริสุทธิ์ข้างบนคำนวณสถานะใหม่

**ห้ามเขียน `events` ตรง ๆ ด้วย SQL** รวมถึงสคริปต์นำเข้าข้อมูล ไม่งั้น `สถานะปัจจุบัน`
จะเพี้ยนโดยไม่มีอะไรเตือน และต้องมีคำสั่งสร้าง `people` ใหม่จาก `events` ทั้งหมดได้เสมอ
ซึ่งเป็นทั้งเครื่องมือกู้และเครื่องมือทดสอบว่า projection ถูก

### สิทธิ์เข้าถึง

RLS เปิดทุกตาราง policy คือ "ผู้ใช้ที่ล็อกอินแล้วเห็นได้"
เจ้าหน้าที่ทุกคนเห็นและแก้ข้อมูลทั้งหมด ไม่กั้นตามเจ้าของเคส
([ADR-0004](../../docs/adr/0004-no-access-partitioning.md)) — คนนอกต้องไม่เห็นอะไรเลย

เลขบัตรประชาชนเก็บเข้ารหัสด้วย `pgcrypto` คีย์อยู่ใน Supabase Vault
ถอดผ่านฟังก์ชัน `security definer` ที่เขียน log ทุกครั้ง หน้าจอปกติเห็น 4 ตัวท้าย

### ค้นหา

ใช้ trigram index บนชื่อและชื่อ Facebook — Postgres ตัดคำไทยไม่ได้
ถ้าใช้ full-text search ตามปกติ ค้น "ศิริ" จะไม่เจอ "ศิริพร"

### นำเข้าข้อมูลเดิม

สคริปต์แยกต่างหาก มีโหมด dry-run ที่ออกรายงานก่อนเขียนจริง ต้องทำ:

- ยุบชื่อคณะ 64 ค่าเหลือ 10 · สาขา 90 เหลือประมาณ 25 · วุฒิ 43 เหลือ 5
- ลบวรรณยุกต์ซ้ำในชื่อเจ้าหน้าที่ แล้ว map เข้า `staff`
- แยกสถานะออกจากช่องวันที่ (1,486 จาก 1,530 แถวไม่ใช่วันที่)
- แปลงวันที่ข้อความหลายรูปแบบเป็น timestamp
- แตกคอลัมน์ติดตาม 6 ช่องเป็นเหตุการณ์ `โทรตาม` แยกแถว (1,204 รายการ)
- ตรวจจับชื่อซ้ำ 122 แถวและเบอร์ซ้ำ 16 แถว แล้วรายงานให้คนตัดสิน ไม่รวมอัตโนมัติ
- แถวที่แปลงไม่ได้ต้องรายงาน ไม่ใช่เงียบ ๆ ข้าม

### หน้าจอ

กระดานงานค้างเป็นหน้าแรก มีแถบตัวเลขรวมด้านบน ไม่มีตัวเลขรายบุคคลของเจ้าหน้าที่
รายละเอียดการออกแบบอยู่ใน [docs/PROMPT-design.md](../../docs/PROMPT-design.md)

## Testing Decisions

**ยังไม่มี test ในโปรเจกต์นี้เลย** ไม่มี prior art — spec นี้เป็นตัวตั้งแบบแผน
ใช้ Vitest สำหรับ seam หลัก และ Playwright สำหรับ smoke test

ทดสอบ **พฤติกรรมที่เห็นจากภายนอก** เท่านั้น ไม่ทดสอบว่าข้างในเรียกฟังก์ชันอะไร
ตัวอย่างที่ดี: "บันทึกเหตุการณ์ดรอป แล้วสถานะการเรียนต้องกลายเป็นดรอป
โดยสถานะการเงินไม่เปลี่ยน" ตัวอย่างที่ไม่ดี: "ฟังก์ชัน applyEvent ถูกเรียก 1 ครั้ง"

### Seam 1 — โมดูลโดเมน (หลัก)

ส่วนที่เป็นฟังก์ชันบริสุทธิ์ ทดสอบโดยไม่ต้องมีฐานข้อมูล ครอบคลุมให้ละเอียด:

- เหตุการณ์แต่ละชนิดใน 15 ชนิด เปลี่ยนสถานะมิติไหนบ้าง
- **เคสที่พิสูจน์ว่า 3 มิติแยกกันจริง**: รักษาสภาพแล้วสถานะการเรียนต้องไม่เปลี่ยน ·
  ชำระครบแล้วดรอป สถานะการเงินต้องยังเป็นชำระครบ
- ลำดับเหตุการณ์ที่ผิดธรรมชาติ เช่น กลับมาเรียนโดยไม่เคยดรอป
- เหตุการณ์ที่บันทึกย้อนหลังแล้วมาแทรกกลางลำดับ
- ดรอปแล้วเกิดเครดิต และกลับมาเรียนแล้วเครดิตถูกใช้
- การเล่นเหตุการณ์ทั้งชุดซ้ำต้องได้สถานะเดียวกันเสมอ

ส่วนที่แตะฐานข้อมูล ทดสอบกับ Supabase local จำนวนน้อย:

- บันทึกเหตุการณ์แล้ว `people` อัปเดตตาม และสร้าง `people` ใหม่จาก `events` ได้ค่าเดิม
- **RLS: ผู้ใช้ที่ยังไม่ล็อกอินเรียก API ตรง ๆ ต้องไม่ได้ข้อมูลเลย** — เส้นที่ห้ามพลาด
- การถอดรหัสเลขบัตรประชาชนเขียน log ทุกครั้ง

### Seam 2 — Playwright smoke (บาง)

3 เคสเท่านั้น: เข้าสู่ระบบ · เพิ่มผู้สนใจ · บันทึกผลการโทร

· คอมโพเนนต์ UI รายตัว · สคริปต์นำเข้าข้อมูลแบบครอบคลุม (ทดสอบเฉพาะฟังก์ชันแปลงค่า

## Out of Scope

- **หน้าสมัครสาธารณะ** — ผู้สนใจ 90% มาทาง Facebook มีเบอร์แค่ 19% ฟอร์มยังไม่ตรงกับวิธีที่คนเข้ามาจริง
- **การจัดส่ง Box set / เอกสาร / เลข tracking** — เป็นสายพานหลังชำระเงิน เลื่อนไปรอบถัดไป
- **คำขอข้ามฝ่าย** (ขอใบเสร็จ ขอรหัส นศ. จากหน่วยงานอื่นอย่างเป็นระบบ)
- **เหตุการณ์เกี่ยวกับ กยศ.**
- **แจ้งเตือนเข้ากลุ่ม LINE** — วางโครงไว้แล้วแต่ยังไม่เปิดใช้
- **รายงาน conversion และกราฟ** — รอให้ทีมใช้จริง 2 สัปดาห์ก่อน
- **ระบบตั้งเวลาโพสต์ Facebook · ระบบลงเวลาทำงาน · LMS** — มีเครื่องมือที่ดีอยู่แล้ว
- **การซิงก์อัตโนมัติกับระบบมหาวิทยาลัย** — ทีมไม่มีสิทธิ์เข้าถึง
