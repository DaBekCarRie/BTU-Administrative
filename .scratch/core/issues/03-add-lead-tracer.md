## ผลการตรวจ

**เกณฑ์ที่สำคัญที่สุด — สร้าง `คน` ใหม่จาก `เหตุการณ์` แล้วได้ผลเท่าเดิม**
ไม่ได้ตรวจแค่ "รันแล้วบอกว่าไม่ต่าง" แต่ทำข้อมูลพังโดยตั้งใจก่อน:

```
ทำ people ทุกแถวพัง →  db:verify  พบต่างกัน 5/5 ราย
                    →  db:rebuild เขียนใหม่ 5 ราย
                    →  db:verify  ตรงกันหมด ✓
```

ข้อมูลกลับมาครบ รวมถึงคนที่เคยแก้ไข — เบอร์ `0877777777` กับชื่อเล่น `เล่นใหม่`
มาจากเหตุการณ์ `แก้ไขข้อมูล` ไม่ใช่ตอนสร้าง แปลว่าการเล่นเหตุการณ์ซ้ำถูกต้องจริง

**ยามเฝ้าตาราง people** พิสูจน์แล้วว่า `insert` ตรง ๆ ถูกปฏิเสธ (0 แถวเล็ดลอด)
กฎ "ห้าม UPDATE people ตรง ๆ" จึงบังคับที่ฐานข้อมูล ไม่ใช่แค่เขียนไว้ใน CLAUDE.md

## บั๊กจริงที่เจอระหว่างทำ — `signOut` เตะผู้ใช้ออกทุกเครื่อง

เทสต์ leads ล้มเฉพาะตอนรันพร้อมไฟล์ login สืบแล้วพบว่า `supabase.auth.signOut()`
ตั้งต้นเป็น scope `global` คือเพิกถอน session ของผู้ใช้คนนั้นทุกเครื่อง

แปลว่าในการใช้งานจริง เจ้าหน้าที่กดออกจากระบบบนมือถือ แล้วจะหลุดจากเครื่องคอมด้วย
แก้เป็น `scope: "local"` แล้ว — เทสต์ผ่านทั้ง 10 ทันที

**สมมติฐานแรกผิด** ตอนแรกเดาว่าเป็นเพราะ dev server ของ Next คอมไพล์ route ช้า
จึงย้ายไปรันเทสต์กับ production build ซึ่งไม่ได้แก้ปัญหา แต่เก็บไว้เพราะใกล้ของจริงกว่า

## การตัดสินใจเชิงออกแบบ

- **projection อยู่ใน TypeScript ไม่ใช่ SQL trigger** ตามที่ spec เลือก seam ไว้
  ฐานข้อมูลรับหน้าที่เฉพาะ "เขียนสองตารางในทรานแซกชันเดียว" ผ่าน `record_event()`
  ที่รับสถานะซึ่ง TS คำนวณมาแล้ว
- **`DomainEvent` ใน TS มีแค่ 2 ชนิด** (`ติดต่อเข้ามา`, `แก้ไขข้อมูล`) ทั้งที่ enum
  ในฐานข้อมูลมีครบ 15 ตั้งใจให้ `switch` เป็น exhaustive — ใบถัดไปเพิ่มชนิดใน union
  แล้ว TypeScript จะบังคับให้เขียน handler เอง ลืมไม่ได้
- **ไม่ใส่ unique constraint บนเบอร์โทร** เพราะบางเบอร์ใช้ร่วมกันในครอบครัวจริง
  การกันซ้ำเป็นการเตือนให้คนตัดสิน (ใบ 07) ไม่ใช่บล็อกที่ฐานข้อมูล
- เพิ่มหน้าแก้ไขข้อมูล (`/leads/[id]/edit`) เพราะเกณฑ์ข้อ `แก้ไขข้อมูล`
  พิสูจน์ไม่ได้ถ้าไม่มีทางเดินจริงในหน้าจอ

## เก็บกวาด

- อัปเกรด `@types/node` จาก ^20 เป็น ^24 ให้ตรงกับ Node ที่รันอยู่ (vitest 5 ต้องการ)
