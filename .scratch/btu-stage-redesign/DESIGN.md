## 2. แบบจำลองสถานะ

```
                    ┌─ follow_up_status  (ใช้เฉพาะขั้นนี้)
   ผู้สนใจ ─────────┤   ใหม่ · กำลังติดตาม · นัดโทรแล้ว · สนใจสมัคร
      │             └─ next_call_at, คิวโทร, งานโทรตาม
      │  เปลี่ยนขั้น + ยื่นสมัคร (ฟอร์มเดียว)
      ▼
   นักศึกษา ────────┬─ enrollment_status  ยังไม่เริ่ม · เรียนอยู่ · ดรอป · ลาออก · จบแล้ว
      │             └─ payment_status     ยังไม่ชำระ · ผ่อนอยู่ · รักษาสภาพ · ชำระครบ
      │                (สองมิตินี้เป็นสำเนาจากทะเบียน/การเงิน — ADR-0003)
      │  เปลี่ยนขั้น + ต้องกรอกเหตุผล
      ▼
   ปิดแฟ้ม ─────────── ไม่สนใจ · ติดต่อไม่ได้ · ลาออก · จบแล้ว
```

ย้อนทางได้ทุกทิศ ผ่านเหตุการณ์ `เปลี่ยนขั้น` · ย้อนกลับและปิดแฟ้มต้องกรอกเหตุผล เดินหน้าไม่ต้อง

**สามมิติเดิมอยู่ครบ** ไม่ยุบรวมตาม ADR-0002 แต่แต่ละมิติมีขั้นที่มันมีความหมายเท่านั้น หน้าจอซ่อนมิติที่ไม่เกี่ยวกับขั้นปัจจุบัน — ลดช่องที่ทีมต้องมองจาก 3 เหลือ 1–2

### ทำไมระบบไม่เปลี่ยนขั้นให้เอง

เมื่อผู้ใช้เลือก "กดตั้งเองได้" การให้ระบบแอบเปลี่ยนขั้นตอนมีเหตุการณ์อื่นจะทำให้มีสองมือที่เขียนคอลัมน์เดียวกัน แล้วเจ้าหน้าที่จะเจอค่าที่ตัวเองไม่ได้ตั้ง ดังนั้น:

- บันทึกโทรตามบนแฟ้มที่ `ปิดแฟ้ม` → **ไม่เปิดแฟ้มกลับเอง** บันทึกได้ปกติ ถ้าตั้งนัดโทรใหม่ก็ขึ้นป้ายข้อ 4 ให้คนตัดสินใจเอง
- ยื่นสมัครโดยไม่เปลี่ยนขั้น → ไม่เลื่อนขั้นเอง ขึ้นป้ายข้อ 1
- เหตุการณ์ `ลาออก` / `จบแล้ว` → ไม่ปิดแฟ้มเอง ขึ้นป้ายข้อ 5

ป้ายเตือนคือราคาที่จ่ายเพื่อแลกกับการควบคุมด้วยมือ ซึ่งเป็นสิ่งที่เลือกไว้แล้ว

## 3. เหตุการณ์ใหม่ 3 ตัว

`event_type` เป็น enum ใน Postgres ต้องเพิ่มค่าผ่าน `alter type ... add value` ตามแบบ `20260911211139_add_confirm_status_event.sql`

### `เปลี่ยนขั้น`
```ts
payload: {
  from: PersonStage | null;     // null = ตอน backfill
  to:   PersonStage;
  reason?: string | null;        // บังคับเมื่อ to เป็น 'ปิดแฟ้ม' หรือเป็นการย้อนจาก 'นักศึกษา'
}
```
reducer → `state.stage = payload.to` · ไม่แตะสามมิติเดิมเลย

### `รับทราบว่าขั้นไม่ตรง`
```ts
payload: {
  stage: PersonStage;            // ขั้น ณ ตอนที่รับทราบ
  applicationIds: string[];      // ใบสมัครที่ยังไม่ยกเลิก ณ ตอนนั้น เรียง sort แล้ว
  reason: string;                // บังคับ
}
```
reducer → `state.conflictAck = { stage, applicationIds }` (เก็บเป็น jsonb ใน `people.conflict_ack`)

ป้ายขึ้นเมื่อ **มีสภาพขัดกัน** และ (**ไม่เคยรับทราบ** หรือ **ลายนิ้วมือปัจจุบัน ≠ ลายนิ้วมือที่รับทราบล่าสุด**)
ไม่ต้องมีปุ่มถอนการรับทราบ — เหตุการณ์ล่าสุดชนะอยู่แล้วตามโครง event log

### `ยกเลิกใบสมัคร`
```ts
payload: { applicationId: string; reason: string }
```
ปิดช่องว่างที่เจอตอนตรวจ: `application_status` มีค่า `ยกเลิก` แต่ไม่มีเหตุการณ์ใดพาไปถึงได้ ใบสมัครเข้าระบบแล้วออกไม่ได้

## 4. เงื่อนไขป้ายเตือน 5 แบบ

| # | ขั้น | สภาพ | ทำไมสำคัญ |
|---|---|---|---|
| 1 | `ผู้สนใจ` | มีใบสมัครที่สถานะ ≠ `ยกเลิก` | กรวยนับคนนี้เป็นผู้สนใจ ทั้งที่จ่ายเงินแล้ว |
| 2 | `นักศึกษา` | ไม่มีใบสมัคร หรือมีแต่ `ยกเลิก` ทั้งหมด | ไม่มีปีการศึกษา คณะ สาขา ที่จะอ้างได้เลย |
| 3 | `ปิดแฟ้ม` | มีใบสมัครที่ยังไม่ `ยกเลิก` และยังไม่ `อนุมัติ` | ใบค้างกลางทางที่ไม่มีใครตามต่อ |
| 4 | `ปิดแฟ้ม` | `next_call_at` ยังอยู่ในอนาคต | ปิดแฟ้มแล้วแต่ยังโผล่ในคิวโทรทุกวัน |
| 5 | ทุกขั้น | `enrollment_status = 'เรียนอยู่'` แต่ขั้น ≠ `นักศึกษา` | ทะเบียนบอกว่าเรียนอยู่ แต่แฟ้มไม่ใช่นักศึกษา |

ข้อ 4 ผมเพิ่มเอง เพราะกระทบคิวโทรที่ทีมใช้ทุกวันโดยตรง

**คำนวณตอนอ่าน ไม่เก็บเป็นคอลัมน์** — เงื่อนไขอ้างสองตาราง ถ้าเก็บจะล้าสมัยทุกครั้งที่ใบสมัครเปลี่ยนโดยไม่มีเหตุการณ์ฝั่งคน และต้องเพิ่มเข้า `apply_person_state()` อีกตัวโดยไม่ได้อะไรกลับมา ป้ายเตือนไม่ต้องกรองระดับ index

**ขึ้น 3 ที่** — แถบเตือนในหน้าแฟ้ม (บอกว่าขัดเรื่องอะไร) · ไอคอนในแถวตารางผู้สนใจ + ตัวกรอง "เฉพาะแฟ้มที่ขัดกัน" · ไทล์ที่ 7 ในกระดานงานค้าง ผ่าน `work_board_counts()` ที่นับในฐานข้อมูลอยู่แล้ว

create type public.person_stage  as enum ('ผู้สนใจ', 'นักศึกษา', 'ปิดแฟ้ม');
create type public.title_prefix  as enum ('นาย', 'นาง', 'นางสาว', 'พระ');
create type public.degree_level  as enum ('ปริญญาตรี', 'ปริญญาโท', 'ปริญญาเอก');
create type public.funding_type  as enum ('ชำระตรง', 'กู้ กยศ.');
create type public.shirt_size    as enum ('S', 'M', 'L', 'XL', '2XL', '3XL');
create type public.lead_source   as enum ('Facebook', 'LINE', 'Walk in', 'โทรเข้า', 'แนะนำต่อ', 'อื่นๆ');
create type public.box_set_state as enum ('ยังไม่ส่ง', 'ส่งแล้ว', 'รับเองที่มหาวิทยาลัย');

ทุกค่าสกปรกใน Excel ถูกบีบลงมาเป็น enum ตามกฎเหล็กข้อ 4 — ไซส์เสื้อ 16 ค่า → 6 · แหล่งทุน 7 ค่า → 2 · ระดับชั้น 3 ค่า (`ป.ตรี` `ป.ตรีี` `ป.ตรี`) → 1

### `applications` — ของแต่ละปีที่สมัคร

**ตรงนี้ผมแก้คำตอบ Q3 ที่ตกลงกันไว้** ตอนนั้นจัด 4 ฟิลด์นี้ไว้ที่ `people` ซึ่งผิด เพราะมันเปลี่ยนได้ทุกปีที่สมัครใหม่

| `degree_level` | `degree_level` | คนเดียวสมัคร ป.ตรี ปีนี้ ป.โท ปีหน้า — Excel 2570 มี `ป.โท` ของคนที่จบ ป.ตรี ที่นี่ |
| `funding_type` | `funding_type` | Excel 2569 มี `รอกู้ปี70` คือคนที่เปลี่ยนจากกู้เป็นชำระตรงระหว่างปี |
| `shirt_size` | `shirt_size` | ได้เสื้อต่อปีที่สมัคร ไม่ใช่ต่อคน |
| `box_set_state` | `box_set_state` | ของแจกต่อปี |

### `exam_center_requests` — เพิ่มตามดีไซน์
`province text` · `submitted_at date` · จำนวนผู้ขอร่วมศูนย์นับจาก `count(*) group by center_name` ไม่เก็บซ้ำ

### `documents` — เพิ่มตามดีไซน์
`file_size bigint` เก็บตอนอัปโหลด (ดีไซน์แสดง "ขนาดไฟล์")

### `document_access_log` — เพิ่มตามดีไซน์
`kind text` (ชนิดข้อมูลที่เปิดดู) · `source text` (เปิดจากหน้าไหน) · กรองได้ + ส่งออก CSV ผ่าน route handler ที่มีด่านตรวจสิทธิ์ของตัวเอง (กฎเหล็กข้อ 8)

### สิ่งที่ผมตัดสินว่า**ไม่ทำ**

**สถานะค่าเทอมรายเทอม** — Excel 2568 มี 3 ช่อง (`ค่าเทอม1/68` `2/68` `3/68`) เก็บคำว่า `ครบ` `ดรอป` `ขอผ่อนชำระ` แต่ **ชีต 2569 และ 2570 ตัดทิ้งเหลือช่องเดียว** นั่นคือหลักฐานว่าทีมเลิกติดตามแบบนี้เอง ของที่มีอยู่แล้ว (`payment_status` ต่อคน + ตาราง `payments` รายรายการพร้อมเลขใบเสร็จและวันที่) ตอบได้ว่าจ่ายไปเท่าไรเมื่อไหร่ ซึ่งละเอียดกว่าคำว่า "ครบ"

ถ้าภายหลังพบว่าต้องมีจริง ค่อยเพิ่มตาราง `term_fees` ได้โดยไม่ต้องรื้ออะไร

**ฟิลด์ที่ตัดตาม Q3** — ทุน (12%) · สัมภาษณ์ กยศ. และผลการกู้ (0–3% และว่างเปล่าใน 2 จาก 3 ชีต) · จัดส่งใบเสร็จและบัตรนักศึกษาในชีต 2569/2570 (1%) · ลำดับ (เลขแถว Excel) → ลงช่องหมายเหตุหรือเป็นเหตุการณ์ ไม่สร้างคอลัมน์ที่ว่าง 97%

## 7. Dashboard หัวหน้าทีม

หน้าแรกปัจจุบันเป็น dashboard ของเจ้าหน้าที่อยู่แล้ว — กรวย 5 ขั้น (`ติดต่อเข้ามา → สนใจสมัคร → ยื่นสมัคร → ชำระแล้ว → ได้รหัสนักศึกษา`) เทียบเดือนต่อเดือน กรองคณะ/ภาค/ย้อนหลังได้ + กระดานงานค้าง + คิวโทร **ไม่ทำซ้ำ** หน้าใหม่ตอบสิ่งที่ของเดิมตอบไม่ได้

### 1. ช่องทางไหนคุ้ม — `channel_conversion(p_from, p_to)`
คืน `source · ผู้สนใจ · ยื่นสมัคร · นักศึกษา · อัตราแปลง`
Excel มี Facebook 2,967 ราย กับ LINE 293 ราย แต่ไม่มีใครรู้ว่าช่องทางไหนแปลงเป็นนักศึกษาได้กี่ % เพราะคนสนใจอยู่ชีต `รายละเอียด` คนสมัครอยู่ชีต `สมัครเรียน25xx` เชื่อมกันไม่ได้ — นี่คือเหตุผลที่ต้องเพิ่ม `people.source`

### 2. ใครถือเคสเท่าไรและตามทันไหม — `staff_workload()`
คืน `ผู้ดูแล · เคสที่เปิดอยู่ · เคสค้างเกิน 7 วัน · เลื่อนเป็นนักศึกษาได้เดือนนี้`
Excel: `พรทิวา 699 · ข้าวโอ๊ต 530 · หญิง 474 · ฝ้าย 243` ภาระต่างกัน 3 เท่า และไม่มีตัวเลขว่าใครตามไม่ทัน

### 3. สาขาไหนคนสนใจเยอะแต่ปิดได้น้อย — `program_conversion(p_from, p_to)`
คืน `คณะ · สาขา · ผู้สนใจ · ยื่นสมัคร · นักศึกษา · อัตราแปลง`
บริหารธุรกิจกินความสนใจ 1,410 จาก 3,294 ราย คือ 43% แต่ไม่รู้ว่าแปลงได้เท่าไร

ทั้งสามนับในฐานข้อมูลผ่าน function แบบเดียวกับ `work_board_counts()` ไม่ดึงแถวมานับใน TypeScript — บทเรียนที่เขียนไว้ในหัว migration `20260912014917` ว่าของเดิม `.limit(1000)` ตัดเงียบ ๆ

**ตัวเลขไหนนับจากไหน (Q12)** — จำนวนคนนับจาก `people.stage` เพราะทีมตั้งค่าเอง ต้องเห็นผลที่ตัวเองตั้ง · เงินและใบสมัครนับจาก `applications` + `payments` เพราะต้องกระทบยอดกับฝ่ายการเงินได้ · บวกตัวเลขที่สาม "แฟ้มที่ขัดกัน" ซึ่งควรเป็น 0 ในวันที่ทุกอย่างถูก

## 8. การนำเข้าข้อมูลและ backfill

### backfill คอลัมน์ `stage` สำหรับ 3,177 แถวที่มีอยู่

**ต้องสร้างเป็นเหตุการณ์ ไม่ใช่ `update people set stage = ...`** เพราะ `people` เป็น projection — `npm run db:rebuild` เล่นเหตุการณ์ซ้ำแล้วเขียนทับทุกคอลัมน์ ค่าที่ไม่มีเหตุการณ์รองรับจะถูกล้างเป็นค่า default เงียบ ๆ ตรงกับที่ `credit_balance` เคยเกือบโดน (`20260911211246_apply_person_state_with_credit.sql` เขียนเตือนไว้ที่หัวไฟล์)

```
กฎการแมป (migration เดียว รันครั้งเดียว)
  มีใบสมัครที่สถานะ ≠ 'ยกเลิก'              → 'นักศึกษา'
  follow_up_status ∈ ('ไม่สนใจ','ติดต่อไม่ได้') → 'ปิดแฟ้ม'
  enrollment_status ∈ ('ลาออก','จบแล้ว')      → 'ปิดแฟ้ม'
  ที่เหลือ                                   → 'ผู้สนใจ'

สร้าง events แถวละ 1 รายการ
  type        = 'เปลี่ยนขั้น'
  occurred_at = people.last_event_at   (ไม่ใช่ now() — ไม่งั้นทุกแฟ้มจะดูเหมือนเพิ่งขยับวันนี้)
  recorded_by = null                   (คอลัมน์นี้ nullable อยู่แล้ว)
  payload     = { from: null, to: <ขั้น>, reason: 'ตั้งค่าเริ่มต้นตอนเพิ่มคอลัมน์ขั้น' }
```

แถวที่ `follow_up_status = 'สมัครแล้ว'` (ค่าที่เลิกใช้ตาม Q20) → เปลี่ยนเป็น `'สนใจสมัคร'` แล้วขั้นไปตามกฎข้างบน

ปิดงานด้วย `npm run db:verify` ต้องผ่าน — ถ้าไม่ผ่านแปลว่า reducer กับ `apply_person_state()` ยังไม่ตรงกัน

### นำเข้าข้อมูลจริงจาก Excel (ขั้นท้ายสุด ตาม Q6)

ลำดับ: `รายละเอียด` (3,294) ก่อน แล้ว `สมัครเรียน2568/2569/2570` (309) ค่อยรวมแฟ้มคนที่อยู่ทั้งสองฝั่งด้วยเบอร์โทรที่ผ่าน `normalizePhone()` ผ่านเหตุการณ์ `รวมข้อมูล` ที่มีอยู่แล้ว

**ก่อน import ผมจะทำตารางเทียบให้ตรวจทุกบรรทัด ไม่แมปเองเงียบ ๆ** — คณะ 64 ค่า → 11 · สาขา 90 ค่า → ~30 · วุฒิ 43 ค่า → 6 · ผู้ดูแล 16 ค่า → 5–6 คน · ไซส์เสื้อ 16 → 6 · แหล่งทุน 7 → 2

ของที่แมปตรง ๆ ไม่ได้ ต้องตัดสินตอนทำตารางเทียบ:
- ช่อง `วัน/เดือน/ปีที่ให้โทร` มีค่าที่ไม่ใช่วันที่ — `สมัครแล้ว` 97 แถว · `ไม่ต้องโทร` 38 · `ไม่สมัคร` 27 → ไปเป็นขั้นและเหตุผลปิดแฟ้ม ไม่ใช่วันที่
- ช่อง `ติดตาม` 6 ช่องยัดทุกอย่างในข้อความเดียว (`ฝ้ายโทร 25/03/2025 สนใจสมัครเรียน ให้โทรกลับหลังสงกรานต์`) → แกะเป็นเหตุการณ์ `โทรตาม` แยกฟิลด์ ช่องที่แกะไม่ออกยกข้อความดิบไว้ใน `note` พร้อมธง "นำเข้าจากไฟล์เดิม" ดีกว่าเดาวันที่ให้
- วันเกิดเป็น serial number ปน text ปน `-` (`39234` / `24/3/2004` / `237215` ซึ่งเกินช่วงวันที่ของ Excel)
- `Sheet1` (41 แถว) ซ้ำกับ 2568 ทั้งหมด → ข้าม
- `Sheet2` `Sheet3` ว่าง → ข้าม
- `สมัครเรียน2570` มีแถวจริง 6 แถว ที่เหลือ 94 แถวมีแต่เลขลำดับ → import แค่ 6

## 10. ของที่จะพังและต้องแก้ตาม

- **`log-call.spec.ts`** — ผลโทร `สมัครแล้ว` เปลี่ยนพฤติกรรมจาก "เปลี่ยนสถานะติดตาม" เป็น "สร้างใบสมัคร + เลื่อนขั้น" เทสต์นี้พังแน่
- **`queue.spec.ts` · `leads.spec.ts`** — selector ที่อิงข้อความ 10 จุดต่อไฟล์ และทั้งสองหน้าถูกจัดโครงใหม่
- **`work-board.spec.ts`** — ไทล์เพิ่มจาก 6 เป็น 7
- **`home.spec.ts` · `reference.spec.ts`** — สองหน้านี้ไม่มีในดีไซน์แต่มีเทสต์อยู่จริง **ไม่ลบ** จนกว่าจะสั่ง
- **ค่า `สมัครแล้ว` ที่ค้างใน enum** — ไม่มีอะไรบังคับว่าจะไม่มีใครเผลอใช้อีก ต้องเขียน comment ใน migration และ `/** @deprecated */` ใน `events.ts`
- **`db:rebuild` หลังเพิ่มคอลัมน์** — ถ้าลืมเพิ่มคอลัมน์ใหม่เข้า `apply_person_state()` ข้อมูลจะหายเงียบ ๆ ตอน rebuild ไม่ใช่ตอนเขียน
