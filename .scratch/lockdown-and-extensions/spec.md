Status: ready-for-agent

## Problem Statement

รอบแรกทำครบ 15 ใบและรอบ UI ทำครบ 4 ใบแล้ว แต่การตรวจงานพบปัญหาที่ต้องแก้ก่อนเปิดใช้จริง
และทีมขอของเพิ่มอีกสามอย่าง รวมเป็นสี่เรื่องที่พันกันอยู่

**1. ใครก็ตามที่มีบัญชี Google จะอ่านข้อมูลทั้งหมดได้ทันทีที่เปิดใช้ปุ่มลงชื่อเข้าใช้ด้วย Google**

ระบบเพิ่งเพิ่มปุ่มลงชื่อเข้าใช้ด้วย Google ไว้ แต่ policy ของฐานข้อมูลทุกตารางยังเขียนว่า
"ผู้ที่ล็อกอินแล้วเห็นได้" ซึ่งเคยถูกต้องตอนที่บัญชีทั้งหมดถูกสร้างด้วยมือโดยหัวหน้าทีม
พอเปิด Google ใครสมัครก็กลายเป็น "ผู้ที่ล็อกอินแล้ว" ทันที สมมติฐานเดิมจึงพังทั้งหมด

ทดสอบบนฐานข้อมูลจริงแล้วว่าผู้ที่ล็อกอินแต่**ไม่มีแถวเจ้าหน้าที่**อ่านได้: คน 3,434 ราย ·
เหตุการณ์ 6,497 รายการ · เอกสาร 52 · การชำระเงิน 27 มีสองทางที่ทะลุ:

- หน้าส่งออกรายชื่อเป็นไฟล์ เป็น route handler ซึ่ง**ไม่วิ่งผ่าน layout** จึงไม่ถูกด่านที่หน้าจออื่นมี
- ถือ token ยิง API ของฐานข้อมูลตรง ๆ ข้ามแอปทั้งก้อน — policy เป็นด่านเดียวและมันปล่อยผ่าน

ด่านที่มีอยู่สองจุดกันได้แค่**หน้าจอ** ไม่ได้กัน**ข้อมูล**

**2. ข้อมูลส่วนบุคคลจริงของคนกว่าสามพันรายนอนอยู่ในฐานข้อมูลที่ยังไม่ปลอดภัยพอ**

ชื่อจริง 3,211 · เบอร์โทร 657 · ชื่อ Facebook 2,876 · เลขบัตรประชาชน 12 · ไฟล์ในที่เก็บ 52
ซึ่งมีสำเนาบัตรประชาชนจริง ขณะเดียวกันชุดทดสอบอัตโนมัติก็เขียนลงฐานเดียวกันนี้ทุกรอบ
(เพิ่มมาแล้ว 223 แถว) จนข้อมูลทดสอบปนกับข้อมูลจริงจนแยกยาก

**3. เอกสารที่ไม่ใช่ของรายคนไม่มีที่อยู่ในระบบ**

ทีมมีตารางสอบแต่ละปี ปฏิทินการศึกษา แบบฟอร์ม ประกาศ และรูปประชาสัมพันธ์ ที่ต้องเปิดดูบ่อย
วันนี้ของพวกนี้อยู่ในแชท LINE และไดรฟ์ส่วนตัว หาไม่เจอเวลาต้องใช้ ตารางเอกสารที่มีอยู่
ผูกกับรายคนแบบบังคับและมีแค่สี่ประเภทที่ตรวจผ่าน/ไม่ผ่านได้ จึงใส่ของพวกนี้ไม่ได้เลย

**4. ตอบไม่ได้ว่าเดือนนี้ดีขึ้นหรือแย่ลง**

กระดานงานค้างบอกได้ว่า "วันนี้มีอะไรค้าง" แต่ตอบไม่ได้ว่า "จากคนที่ทักเข้ามาเดือนนี้
ไปถึงยื่นสมัครจริงกี่คน" และ "เทียบเดือนที่แล้วแล้วเป็นยังไง" หัวหน้าทีมยังต้องทำ pivot เอง

## Solution

**1. ปิดระบบให้เฉพาะเจ้าหน้าที่ที่ยังใช้งานอยู่** — ย้ายด่านลงไปที่ชั้นฐานข้อมูล ไม่ใช่แค่ชั้นหน้าจอ
policy ทุกตารางเปลี่ยนจาก "ล็อกอินแล้วเห็นได้" เป็น "เป็นเจ้าหน้าที่ที่ยังใช้งานอยู่จึงเห็นได้"
และอุดหน้าส่งออกไฟล์ที่ไม่วิ่งผ่านด่านเดิม จากนั้นผูกบัญชี Google ของหัวหน้าทีมหนึ่งบัญชี
แล้วปิดการสมัครบัญชีใหม่

นี่คือการ**รักษา**เจตนาของ ADR-0004 ไม่ใช่ขัด — ADR นั้นห้ามกั้นข้อมูล*ระหว่างเจ้าหน้าที่*
และเขียนไว้เองว่า "ความต่างอยู่ที่คนนอกยังเข้าไม่ได้เลย" ซึ่งเป็นประโยคที่ปุ่ม Google ทำให้ไม่จริง

**2. แทนข้อมูลจริงด้วยข้อมูลสมมติแบบย้อนกลับได้** — ล้างคนและเหตุการณ์แล้วนำเข้าใหม่จากไฟล์
ที่แทนที่เฉพาะช่องข้อมูลส่วนบุคคล โดยคงจำนวนแถวและความรุงรังของข้อมูลไว้ครบ
(เบอร์ซ้ำ วรรณยุกต์ซ้ำ คณะหลายสิบค่า ช่องวันที่ที่ไม่ใช่วันที่) เพราะความรุงรังนั้นคือสิ่งที่
กฎล้างข้อมูลถูกเขียนมาแก้ ถ้า mock สะอาดเกินไปบั๊กพวกนั้นจะกลับมาโดยไม่มีใครจับได้

**3. เอกสารอ้างอิง** — ของกลางที่ทีมเปิดดูเพื่ออ้างอิง ไม่ผูกกับคนและไม่มีการตรวจผ่าน/ไม่ผ่าน
มีหมวดเป็นค่าคงที่ มีปีการศึกษาสำหรับของที่ผูกกับปี แนบได้หลายไฟล์ต่อรายการ อยู่ในเมนูของตัวเอง

**4. กระดานภาพรวมที่หน้าแรก** — กรวยตั้งแต่ติดต่อเข้ามาจนได้รหัสนักศึกษา แบ่งตามคณะ ภาค และเดือน
เทียบเดือนนี้กับเดือนที่แล้ว เป็นตัวเลขล้วนไม่มีกราฟ และมีคิวโทรวันนี้อยู่ในหน้าเดียวกัน
เพื่อไม่ให้งานหลักของเจ้าหน้าที่จมลงไป

## User Stories

### ปิดสิทธิ์เฉพาะเจ้าหน้าที่

1. As a หัวหน้าทีม, I want คนที่ไม่มีชื่อเป็นเจ้าหน้าที่อ่านข้อมูลของระบบไม่ได้เลยแม้จะล็อกอินสำเร็จ, so that การเปิดปุ่มลงชื่อเข้าใช้ด้วย Google ไม่กลายเป็นการเปิดข้อมูลคนสามพันรายให้คนทั้งอินเทอร์เน็ต
2. As a หัวหน้าทีม, I want คนที่ล็อกอินได้แต่ยังไม่ถูกผูกเป็นเจ้าหน้าที่เห็นแค่หน้าบอกว่ายังไม่มีสิทธิ์, so that รู้ว่าต้องมาขอสิทธิ์ ไม่ใช่เจอหน้าจอพังหรือหน้าว่าง
3. As a หัวหน้าทีม, I want การส่งออกรายชื่อเป็นไฟล์ถูกด่านเดียวกับหน้าจออื่น, so that ไม่มีทางลัดที่เลี่ยงด่านไปได้
4. As a หัวหน้าทีม, I want คนที่ถือ token ยิงเข้าฐานข้อมูลตรง ๆ ก็ยังไม่ได้ข้อมูล, so that ด่านไม่ได้อยู่แค่ที่หน้าเว็บซึ่งเลี่ยงได้
5. As a หัวหน้าทีม, I want เจ้าหน้าที่ที่ถูกปิดการใช้งานเสียสิทธิ์อ่านข้อมูลทันที, so that คนที่ออกจากทีมไปแล้วไม่ยังเข้าได้อยู่
6. As a หัวหน้าทีม, I want ล็อกอินด้วยบัญชี Google ของตัวเองได้, so that ไม่ต้องจำรหัสผ่านอีกชุด
7. As a หัวหน้าทีม, I want ปิดการสมัครบัญชีใหม่หลังผูกบัญชีของตัวเองเรียบร้อย, so that ไม่มีบัญชีแปลกหน้างอกในระบบ
8. As a หัวหน้าทีม, I want บัญชีทดสอบที่ค้างอยู่ถูกลบทิ้ง, so that ไม่มีบัญชีที่ล็อกอินได้แล้วไม่มีใครเป็นเจ้าของ
9. As a หัวหน้าทีม, I want แถวเจ้าหน้าที่ที่ยังไม่มีบัญชีเข้าระบบยังเป็นเจ้าของเคสได้เหมือนเดิม, so that ข้อมูลผู้ดูแลจากชีทเดิมไม่หายไป
10. As a หัวหน้าทีม, I want รวมรายการที่เป็นคนเดียวกันได้จริง, so that ใช้งานฟีเจอร์กันข้อมูลซ้ำได้เป็นครั้งแรก (วันนี้ทำไม่ได้เพราะไม่มีใครเป็นหัวหน้าทีมในระบบ)
11. As a เจ้าหน้าที่, I want ยังเห็นและแก้ข้อมูลของเคสที่เพื่อนร่วมทีมดูแลได้ทั้งหมด, so that งานไม่ค้างเวลามีคนลา (ADR-0004 ไม่เปลี่ยน)
12. As a หัวหน้าทีม, I want มีชุดทดสอบที่พิสูจน์ว่าคนนอกทีมอ่านอะไรไม่ได้, so that ช่องโหว่นี้ไม่กลับมาอีกตอนมีคนแก้ policy ในอนาคต
13. As a หัวหน้าทีม, I want รู้ว่าใครเป็นหัวหน้าทีมในระบบอย่างชัดเจน, so that สิทธิ์ที่ย้อนยาก เช่น การลบและการรวมรายการ อยู่กับคนที่ควรถือ
14. As a เจ้าหน้าที่, I want ข้อความบอกสิทธิ์ใช้คำว่าเจ้าหน้าที่และหัวหน้าทีม, so that ไม่สับสนกับคำว่าแอดมินที่กำกวมกับ role ของระบบ

### แทนข้อมูลจริงด้วยข้อมูลสมมติ

15. As a หัวหน้าทีม, I want ข้อมูลส่วนบุคคลจริงไม่อยู่ในฐานข้อมูลระหว่างที่ยังพัฒนาอยู่, so that ความเสี่ยงต่ำที่สุดระหว่างที่ยังเปิดปิดสิทธิ์และรันชุดทดสอบ
16. As a หัวหน้าทีม, I want นำข้อมูลจริงกลับเข้าระบบได้เมื่อพร้อมใช้งานจริง, so that ไม่เสียของที่เป็นคุณค่าทั้งหมดของระบบนี้ไป
17. As a หัวหน้าทีม, I want ไฟล์สำเนาบัตรประชาชนและเอกสารรายคนจริงถูกลบออกจากที่เก็บด้วย, so that การถอดข้อมูลจริงออกไม่ได้ทำแค่ครึ่งเดียว
18. As a หัวหน้าทีม, I want ชื่อเจ้าหน้าที่จริงถูกแทนด้วยชื่อสมมติทั้งในฐานข้อมูล ในชุดทดสอบ และในเอกสารประกอบ, so that ไม่มีชื่อคนจริงเหลือค้างอยู่ที่ใดในโปรเจกต์
19. As a หัวหน้าทีม, I want คลังคำตอบถูกตรวจและแทนชื่อคนจริงถ้ามี, so that ไม่มีชื่อหลุดผ่านช่องที่นึกไม่ถึง
20. As a เจ้าหน้าที่, I want ข้อมูลสมมติมีความรุงรังเหมือนข้อมูลจริง, so that กฎล้างข้อมูลยังถูกทดสอบจริงและบั๊กเดิมไม่กลับมาเงียบ ๆ
21. As an agent, I want ไฟล์ข้อมูลสมมติอยู่ในที่เก็บโค้ด, so that clone มาแล้วตั้งต้นระบบใหม่ได้เองโดยไม่ต้องพึ่งไฟล์ในเครื่องใครคนหนึ่ง
22. As a หัวหน้าทีม, I want วันที่ติดต่อเข้ามาที่อยู่ในอนาคตถูกปฏิเสธตอนนำเข้า, so that ตัวเลข "เดือนนี้" ไม่เพี้ยนไปเรื่อย ๆ จากค่าที่พิมพ์ผิด
23. As a หัวหน้าทีม, I want เห็นจำนวนวันที่ที่ถูกตัดออกตอนนำเข้า, so that รู้ว่าข้อมูลมีปัญหาแค่ไหน ไม่ใช่ถูกทิ้งไปเงียบ ๆ
24. As a หัวหน้าทีม, I want สถานะปัจจุบันสร้างใหม่จากเหตุการณ์ได้ตรงทุกแถวหลังนำเข้าข้อมูลสมมติ, so that มั่นใจว่าการล้างและนำเข้าใหม่ไม่ทำให้ระบบเสียความถูกต้อง

### เอกสารอ้างอิง

25. As a เจ้าหน้าที่, I want เก็บตารางสอบของแต่ละปีไว้ในระบบ, so that ไม่ต้องไถหาในแชท LINE ตอนผู้เรียนถาม
26. As a เจ้าหน้าที่, I want เก็บปฏิทินการศึกษา แบบฟอร์ม ประกาศ และรูปประชาสัมพันธ์, so that ของที่ใช้บ่อยอยู่ที่เดียวกันหมด
27. As a เจ้าหน้าที่, I want เลือกหมวดของเอกสารอ้างอิงจากรายการที่มีให้, so that หมวดไม่งอกเป็นสิบค่าจากการพิมพ์เองเหมือนที่เคยเกิดกับคณะ
28. As a เจ้าหน้าที่, I want ระบุปีการศึกษาให้เอกสารอ้างอิงที่ผูกกับปีได้ และเว้นว่างได้ถ้าไม่ผูก, so that ตารางสอบแยกปีได้ แต่รูปประชาสัมพันธ์ไม่ต้องถูกบังคับใส่ปี
29. As a เจ้าหน้าที่, I want แนบไฟล์หลายไฟล์ในเอกสารอ้างอิงรายการเดียว, so that ตารางสอบที่มีหลายหน้าหรือหลายภาคอยู่รวมกันเป็นเรื่องเดียว
30. As a เจ้าหน้าที่, I want ตั้งชื่อเรื่องของเอกสารอ้างอิงเอง, so that หาเจอด้วยคำที่ทีมใช้เรียกกันจริง
31. As a เจ้าหน้าที่, I want กรองเอกสารอ้างอิงตามหมวดและปีการศึกษา, so that หาของที่ต้องใช้ได้ในไม่กี่คลิก
32. As a เจ้าหน้าที่, I want ค้นเอกสารอ้างอิงด้วยชื่อเรื่อง, so that พิมพ์คำที่จำได้แล้วเจอเลย
33. As a เจ้าหน้าที่, I want เปิดดูไฟล์เอกสารอ้างอิงได้, so that ตอบคำถามผู้สนใจได้ทันทีระหว่างคุยโทรศัพท์
34. As a เจ้าหน้าที่, I want อัปโหลดและแก้เอกสารอ้างอิงได้ทุกคน, so that ใครเจอของใหม่ก็ใส่เข้าระบบได้เลยไม่ต้องรอหัวหน้า
35. As a หัวหน้าทีม, I want ลบเอกสารอ้างอิงได้เฉพาะหัวหน้าทีม, so that ของกลางที่ทุกคนใช้ไม่หายเพราะคนเดียวเผลอ
36. As a เจ้าหน้าที่, I want เห็นว่าใครอัปโหลดเอกสารอ้างอิงและเมื่อไหร่, so that ถามคนที่รู้เรื่องได้ถ้าไฟล์ดูเก่า
37. As a เจ้าหน้าที่, I want เอกสารอ้างอิงอยู่ในเมนูของตัวเองแยกจากเอกสารรายคน, so that ไม่สับสนกับการตรวจเอกสารซึ่งเป็นงานคนละอย่าง
38. As a เจ้าหน้าที่, I want เอกสารอ้างอิงไม่มีสถานะผ่าน/ไม่ผ่านและไม่มีการบันทึกการเปิดดู, so that ไม่ถูกปฏิบัติเหมือนข้อมูลส่วนบุคคลที่มันไม่ใช่

### กระดานภาพรวมที่หน้าแรก

39. As a หัวหน้าทีม, I want เห็นกรวยตั้งแต่ติดต่อเข้ามาจนได้รหัสนักศึกษาในหน้าเดียว, so that รู้ว่าคนหลุดหายช่วงไหนมากที่สุด
40. As a หัวหน้าทีม, I want เห็นตัวเลขของเดือนนี้เทียบกับเดือนที่แล้วพร้อมส่วนต่าง, so that ตอบได้ว่าดีขึ้นหรือแย่ลง ไม่ใช่เห็นตัวเลขลอย ๆ
41. As a หัวหน้าทีม, I want ย้อนดูได้ถึงหกเดือน, so that เห็นแนวโน้มไม่ใช่แค่ภาพนิ่งของเดือนนี้
42. As a หัวหน้าทีม, I want แบ่งกรวยตามคณะ, so that รู้ว่าคณะไหนคนสนใจเยอะแต่ปิดไม่ได้
43. As a หัวหน้าทีม, I want แบ่งกรวยตามภาค, so that เห็นว่าทางไกลกับปกติต่างกันแค่ไหน
44. As a หัวหน้าทีม, I want ตัวเลขบนกระดานภาพรวมไม่แยกเป็นรายบุคคลของเจ้าหน้าที่, so that ระบบไม่กลายเป็นเครื่องมือวัดผลคนโดยไม่ได้ตั้งใจ
45. As a หัวหน้าทีม, I want ไม่มีกราฟหรือแผนภูมิในรอบนี้, so that ไม่เดาผิดว่าทีมอยากเห็นอะไรก่อนที่ทีมจะได้ใช้จริง
46. As a เจ้าหน้าที่, I want เปิดระบบมาแล้วยังเห็นคิวโทรวันนี้ทันทีในหน้าเดียวกับตัวเลขภาพรวม, so that งานที่ต้องทำทุกวันไม่ถูกดันให้ลึกลงไปอีกคลิก
47. As a เจ้าหน้าที่, I want กระดานงานค้างที่มีอยู่แล้วยังอยู่, so that ไม่เสียของที่เพิ่งทำเสร็จไป
48. As a หัวหน้าทีม, I want กระดานภาพรวมนับคนไม่ใช่นับใบสมัคร, so that คนที่สมัครสองรอบไม่ถูกนับสองครั้ง
49. As a หัวหน้าทีม, I want ตัวเลขไม่ถูกตัดเงียบ ๆ เมื่อข้อมูลโตขึ้น, so that ตัวเลขยังเชื่อได้ตอนมีผู้สนใจหลายหมื่นราย
50. As a หัวหน้าทีม, I want รายการที่วันติดต่อเข้ามาอยู่ในอนาคตไม่ทำให้ตัวเลขเดือนนี้เพี้ยน, so that ตัวเลขที่เห็นตรงกับความจริง
51. As a หัวหน้าทีม, I want เห็นตัวเลขแม้ยังไม่มีการสมัครจริงในระบบ, so that หน้าจอไม่ดูเหมือนพังในวันแรกที่ช่วงปลายกรวยยังว่าง
52. As a เจ้าหน้าที่, I want กระดานภาพรวมใช้บนมือถือได้, so that ดูตัวเลขได้ตอนอยู่นอกสถานที่เหมือนหน้าจออื่นที่เพิ่งปรับไป

## Implementation Decisions

### ปิดสิทธิ์เฉพาะเจ้าหน้าที่

- ด่านคือ **"มีแถวเจ้าหน้าที่ที่ยังใช้งานอยู่"** ไม่ใช่ `role` ใด ๆ เป็นพิเศษ — ใช้ฟังก์ชัน
  `security definer` ที่มีอยู่แล้วซึ่งคืนรหัสเจ้าหน้าที่ของผู้ใช้ปัจจุบัน เป็นตัวตัดสินใน policy
  ฟังก์ชันนี้เป็น `security definer` อยู่แล้วจึงไม่เกิดปัญหาไก่กับไข่เวลาอ่านตารางเจ้าหน้าที่
- **policy ทุกตารางใน schema สาธารณะเปลี่ยนเงื่อนไขเป็นด่านนี้** รวมข้อมูลหลัก (คณะ หลักสูตร)
  และคลังคำตอบ เหตุผล: อธิบายได้ด้วยประโยคเดียวว่า "ไม่ใช่เจ้าหน้าที่ = ไม่เห็นอะไรเลย"
  และไม่มีใครนอกทีมมีเหตุต้องอ่านรายชื่อคณะจากระบบนี้
- policy ของที่เก็บไฟล์เอกสารรายคนใช้ด่านเดียวกัน
- **หน้าส่งออกรายชื่อเป็นไฟล์ต้องมีด่านของตัวเอง** เพราะเป็น route handler ซึ่งไม่วิ่งผ่าน layout
  ตรวจทั้งว่าล็อกอินแล้วและเป็นเจ้าหน้าที่ที่ยังใช้งานอยู่ ถ้าไม่ผ่านตอบ 403 ไม่ใช่ส่งไฟล์ว่าง
- ไล่ตรวจ route handler ทุกตัวในระบบว่ามีด่านของตัวเอง และเขียนกฎข้อนี้ลง `CLAUDE.md`
  เพื่อไม่ให้คนถัดไปเพิ่ม route handler แล้วลืมด่านอีก
- บัญชีที่จะเหลือในระบบ: บัญชี Google ของหัวหน้าทีมหนึ่งบัญชี (`role` หัวหน้าทีม) และ
  **บัญชีทดสอบสามบัญชี** (หัวหน้าทีม / เจ้าหน้าที่ / คนนอกทีมที่ไม่มีแถวเจ้าหน้าที่)
  บัญชีเดิมโดเมนสมมติที่เหลือถูกลบ
- แถวเจ้าหน้าที่ของ 5 คนยังอยู่โดยไม่ผูกบัญชีเข้าระบบ ซึ่งเป็นสิ่งที่ระบบรองรับอยู่แล้วโดยตั้งใจ
- ปิดการสมัครบัญชีใหม่เป็น**งานที่คนต้องทำเองบน Dashboard** หลังยืนยันว่าล็อกอิน Google ผ่าน
  บันทึกไว้ในเอกสารความคืบหน้าเป็นขั้นตอนที่ต้องทำด้วยมือ
- ข้อความสิทธิ์ทั้งหมดใช้คำ **เจ้าหน้าที่** และ **หัวหน้าทีม** ตาม `CONTEXT.md` ซึ่งสั่งเลี่ยงคำว่า
  แอดมิน/admin เพราะกำกวมกับ `role` ของระบบ ค่าใน `role` ยังเป็นภาษาอังกฤษตามเดิมไม่ต้องแก้

### แทนข้อมูลจริงด้วยข้อมูลสมมติ

- **ล้างคนและเหตุการณ์ทั้งหมดแล้วนำเข้าใหม่** ไม่เขียนทับ payload ของเหตุการณ์เดิม
  เพราะ ADR-0001 และ `CONTEXT.md` กำหนดว่าเหตุการณ์บันทึกแล้วไม่ลบไม่แก้
  การแทนข้อมูลจึงต้องเป็น event log ชุดใหม่ทั้งชุด ไม่ใช่การแก้ของเก่า
- สคริปต์สร้างไฟล์นำเข้าสมมติ **แทนที่เฉพาะช่องชื่อ เบอร์โทร และชื่อผู้ดูแล** บนไฟล์จริง
  คงคอลัมน์อื่น จำนวนแถว และลำดับแถวไว้ทั้งหมด และต้องคงคุณสมบัติเหล่านี้:
  - เบอร์โทรที่ซ้ำกันต้องยังซ้ำกันเป็นคู่เดิม (ฟีเจอร์กันข้อมูลซ้ำต้องยังมีของให้จับ)
  - ชื่อที่มีวรรณยุกต์ซ้ำต้องยังมีวรรณยุกต์ซ้ำ (กฎยุบวรรณยุกต์ต้องยังถูกทดสอบ)
  - ชื่อผู้ดูแลที่เขียนหลายแบบต้องยังเขียนหลายแบบ (ตารางแปลงชื่อผู้ดูแลต้องยังถูกใช้)
  - คอลัมน์คณะ สาขา วุฒิ และช่องติดตามที่ปนสถานะกับวันที่ **ไม่แตะเลย**
- ไฟล์นำเข้าสมมติ **เก็บเข้าที่เก็บโค้ด** เพื่อให้ตั้งต้นระบบใหม่ได้เองโดยไม่พึ่งไฟล์ในเครื่องใคร
- ลบไฟล์ทั้งหมดในที่เก็บเอกสารรายคน และล้างแถวเอกสาร การสมัคร การชำระเงิน คำขอศูนย์สอบ
  ที่อ้างถึงคนซึ่งถูกล้างไป
- ชื่อเจ้าหน้าที่จริงถูกแทนด้วยชื่อสมมติในฐานข้อมูล **และในโค้ด**: ตารางแปลงชื่อผู้ดูแลตอนนำเข้า
  เทสต์ของตารางนั้น เทสต์กระดานงานค้างที่ยืนยันว่าชื่อจริงไม่โผล่ และเอกสารออกแบบที่อ้างชื่อ
- ตรวจคลังคำตอบทีละรายการ แทนชื่อคนจริงถ้าพบ
- **ด่านวันที่**: วันติดต่อเข้ามาที่เลยวันนี้ (เวลาไทย) ถือว่าพิมพ์ผิด — *เดิม 30 วัน เปลี่ยนเป็นไม่มีค่าเผื่อในใบ 04* ให้ทิ้งค่าวันที่นั้น
  (ไม่ทิ้งทั้งแถว) และรายงานจำนวนที่ถูกตัดเมื่อจบการนำเข้า แก้ที่ฟังก์ชันบริสุทธิ์ซึ่งมีด่าน
  กัน ±400 วันอยู่แล้ว เพื่อให้ครอบการนำเข้าครั้งต่อ ๆ ไปด้วย ค่านี้ใช้กับวันที่ติดต่อเข้ามาเท่านั้น
  ไม่ใช้กับวันนัดโทรซึ่งต้องเป็นอนาคตโดยธรรมชาติ
- เขียนขั้นตอนนำข้อมูลจริงกลับเข้าระบบไว้ในเอกสารความคืบหน้า
- งานนี้เป็นการเปลี่ยนข้อมูลจริงที่ย้อนยาก ต้องรายงานจำนวนแถวที่จะกระทบให้คนอนุมัติเห็นก่อนลงมือ

### เอกสารอ้างอิง

- คำใหม่ใน `CONTEXT.md`: **เอกสารอ้างอิง** — ของกลางที่ทีมเปิดดูเพื่ออ้างอิง ไม่ผูกกับคน
  ไม่มีการตรวจผ่าน/ไม่ผ่าน (_เลี่ยง_: เอกสาร เฉย ๆ ซึ่งหมายถึงเอกสารประจำตัวของรายคน)
- **ตารางใหม่สองตาราง**: รายการเอกสารอ้างอิง (หมวด ชื่อเรื่อง ปีการศึกษาที่ว่างได้
  ผู้อัปโหลด เวลา) และตารางลูกเก็บไฟล์แนบหลายไฟล์ต่อรายการ
- **หมวดเป็นค่าคงที่** ตาม `CLAUDE.md` กฎข้อ 4: ตารางสอบ · ปฏิทินการศึกษา · แบบฟอร์ม ·
  ประกาศ · สื่อประชาสัมพันธ์ · อื่นๆ (เพิ่มทีหลังได้ด้วย migration เดียว)
- **ปีการศึกษาเก็บเป็น พ.ศ.** ตามแบบเดียวกับปีการศึกษาของการสมัครที่มีอยู่แล้ว ซึ่งเป็น
  ข้อยกเว้นที่ตั้งใจของ `CLAUDE.md` กฎข้อ 5 เพราะปีการศึกษาเป็นป้ายชื่อรุ่นไม่ใช่จุดเวลา
- **ที่เก็บไฟล์แยกเป็นถังใหม่** ไม่ปนกับเอกสารรายคน เพื่อให้เขียน policy ของสองอย่างต่างกันได้
  และกันอุบัติเหตุที่สคริปต์ล้างไฟล์รายคนไปโดนเอกสารอ้างอิง
- สิทธิ์: อ่านและอัปโหลดและแก้ได้ทุกเจ้าหน้าที่ · **ลบได้เฉพาะหัวหน้าทีม** · เก็บผู้อัปโหลดและเวลา
  · **ไม่เขียนบันทึกการเปิดดู** เพราะไม่ใช่ข้อมูลส่วนบุคคล ต่างจากสำเนาบัตรประชาชน
- **เมนูของตัวเองแยกจากเมนูเอกสาร** ไม่ใช่แท็บที่ห้าในหน้าเอกสารรายคน เพราะแท็บที่มีอยู่
  ทั้งหมดเป็นสถานะการตรวจของเอกสารรายคน ซึ่งเป็นมิติคนละเรื่องกัน
- เอกสารอ้างอิง **อยู่นอกระบบเหตุการณ์** — ADR-0001 บังคับว่าการเขียนข้อมูล*คน*ต้องผ่านเหตุการณ์
  เอกสารอ้างอิงไม่ผูกกับคนจึงไม่เข้าข่าย เขียนตารางตรงได้ ต้องมี ADR อธิบายข้อนี้
- เปิดไฟล์ผ่านลิงก์อายุสั้นที่สร้างจากฝั่งเซิร์ฟเวอร์เหมือนเอกสารรายคน ถังเป็นแบบปิดทั้งหมด
- ย่อขนาดรูปก่อนอัปโหลดด้วยกลไกเดียวกับที่เอกสารรายคนใช้อยู่แล้ว

### กระดานภาพรวมที่หน้าแรก

- หน้าแรกเปลี่ยนจากการเด้งไปคิวโทร เป็น **ตัวเลขภาพรวมด้านบน + คิวโทรวันนี้ด้านล่างในหน้าเดียว**
  คิวโทรยังมีเมนูของตัวเองเหมือนเดิมสำหรับคนที่เข้าตรง
- **การนับทำใน SQL function** ตามแบบเดียวกับที่กระดานงานค้างทำอยู่แล้ว เพื่อไม่ให้ถูกตัดเงียบ ๆ
  เมื่อข้อมูลโต และเพื่อ **นับคนไม่ใช่นับใบสมัคร** (ใช้การนับแบบไม่ซ้ำคน)
- ขั้นของกรวย ใช้เหตุการณ์และสถานะที่มีอยู่แล้วเป็นตัวตัดสิน:

  | ขั้น | นับจาก |
  | --- | --- |
  | ติดต่อเข้ามา | เหตุการณ์ `ติดต่อเข้ามา` ในช่วงเวลา |
  | สนใจสมัคร | คนที่สถานะการติดตามไปถึง `สนใจสมัคร` หรือไกลกว่า |
  | ยื่นสมัคร | คนที่มีการสมัครที่สร้างในช่วงเวลา |
  | ชำระแล้ว | คนที่มีการชำระเงินอย่างน้อยหนึ่งงวด |
  | ได้รหัสนักศึกษา | คนที่มีการสมัครที่มีรหัสนักศึกษาแล้ว |

- **ช่วงเวลาคำนวณใน TypeScript** เป็นฟังก์ชันบริสุทธิ์ที่คืนขอบเขตของเดือนตามเวลาไทย
  แล้วส่งเข้า SQL function เป็นพารามิเตอร์ — แยกแบบนี้เพื่อให้ทดสอบการคำนวณเดือน
  ได้ที่ seam เดิมโดยไม่ต้องแตะฐานข้อมูล
- แบ่งตามคณะและภาคเป็นตัวกรองของทั้งกระดาน ไม่ใช่คอลัมน์เพิ่ม
- **ไม่มีกราฟหรือแผนภูมิ** และ **ไม่มีตัวเลขแยกรายบุคคลของเจ้าหน้าที่** (story 55 ของรอบแรก
  และ ADR-0004) — ข้อห้ามสองข้อนี้มีเทสต์คุมอยู่แล้วที่กระดานงานค้าง ต้องมีเทสต์แบบเดียวกัน
  ที่หน้าแรกด้วย
- รายการที่วันติดต่อเข้ามาอยู่ในอนาคตไม่ถูกนับเข้าช่วงเวลาใด ๆ (ด่านนำเข้าจัดการที่ต้นทางแล้ว
  แต่การนับต้องไม่พึ่งด่านนั้นเพียงอย่างเดียว)
- ช่วงปลายกรวยที่ยังไม่มีข้อมูลจริงต้องแสดงศูนย์พร้อมคำอธิบายสั้น ๆ ไม่ใช่ช่องว่างที่ดูเหมือนพัง

## Testing Decisions

**เทสต์ที่ดีในโปรเจกต์นี้** ทดสอบพฤติกรรมที่คนนอกโมดูลมองเห็น ไม่ทดสอบวิธีการข้างใน
ไม่ยืนยันชื่อฟังก์ชันหรือรูปของ SQL แต่ยืนยันว่า "คนนอกทีมอ่านไม่ได้" และ "ตัวเลขบนจอถูก"
เทสต์ต้องพังเมื่อพฤติกรรมเปลี่ยน ไม่พังเมื่อจัดโค้ดใหม่

**Seam ที่ใช้ — ใช้ของเดิมทั้งหมด ยกเว้นข้อเดียว**

| Seam | ทดสอบอะไร | ของเดิมหรือใหม่ |
| --- | --- | --- |
| เทสต์กฎล้างข้อมูลนำเข้า (vitest) | ด่านวันที่ในอนาคต | เดิม |
| เทสต์ตัวช่วยเรื่องวันที่ (vitest) | ขอบเขตเดือนนี้/เดือนที่แล้วตามเวลาไทย | เดิม |
| เทสต์โมดูลโดเมน (vitest) | ไม่ต้องแตะ — งานรอบนี้ไม่เพิ่มชนิดเหตุการณ์ | เดิม |
| เทสต์ยิง API ฐานข้อมูลตรง | การรัด policy ทั้งของคนที่ยังไม่ล็อกอินและของคนนอกทีม | เดิม (ขยาย) |
| เทสต์ผ่านเบราว์เซอร์ (Playwright) | เอกสารอ้างอิง · กระดานภาพรวม · คิวโทรในหน้าแรก · การเตะคนนอกออก | เดิม |
| **ตัวตั้งต้นการล็อกอินหลายสิทธิ์** | ให้เทสต์เลือกสวมสิทธิ์หัวหน้าทีม / เจ้าหน้าที่ / คนนอกทีมได้ | **ใหม่ — seam ใหม่เพียงอันเดียว** |

**seam ใหม่อันเดียวคือการล็อกอินหลายสิทธิ์** ตัวตั้งต้นเดิมล็อกอินบัญชีเดียวแล้วเก็บ session
ไว้ใช้ร่วมกันทุกเทสต์ ขยายให้เก็บสาม session แยกกัน เพราะกฎสิทธิ์ใหม่สามระดับพิสูจน์ไม่ได้เลย
ด้วยบัญชีเดียว และการสลับ `role` กลางรอบทดสอบใช้ไม่ได้เพราะเทสต์รันขนานกัน
ยังต้องเก็บ session ไว้ใช้ซ้ำเหมือนเดิม ไม่ให้แต่ละเทสต์ล็อกอินเองจนชน rate limit

**สิ่งที่ต้องพิสูจน์ให้ได้**

- คนนอกทีมยิง API ตรงแล้วได้ศูนย์แถวทุกตาราง ทุก view และถูกปฏิเสธทุกฟังก์ชัน
  — ทดสอบที่ชั้นข้อมูล เพราะเป็นชั้นที่สำคัญที่สุด (คนถือ token ข้ามแอปได้)
- คนนอกทีมเปิดหน้าเว็บแล้วถูกเตะออก **และ** เปิดหน้าส่งออกไฟล์ไม่ได้
  — สองชั้นนี้พังแยกกันได้จึงต้องคุมทั้งคู่
- เจ้าหน้าที่ลบเอกสารอ้างอิงไม่ได้ ขณะที่หัวหน้าทีมลบได้
- เจ้าหน้าที่ที่ถูกปิดการใช้งานเสียสิทธิ์ทันที
- ด่านวันที่ตัดวันในอนาคตออกและรายงานจำนวน ขณะที่วันนัดโทรในอนาคตยังผ่านได้
- ขอบเขตเดือนถูกต้องตามเวลาไทย รวมช่วงหลังเที่ยงคืนถึงเจ็ดโมงเช้าซึ่งเคยทำให้วันที่เพี้ยนมาก่อน
- สถานะปัจจุบันสร้างใหม่จากเหตุการณ์ได้ตรงทุกแถวหลังนำเข้าข้อมูลสมมติ
- กระดานภาพรวมไม่มีกราฟและไม่มีชื่อเจ้าหน้าที่ — เทสต์แบบเดียวกับที่กระดานงานค้างมีอยู่แล้ว

**Prior art ในที่เก็บโค้ด** เทสต์ยิง API ฐานข้อมูลตรงของคนที่ยังไม่ล็อกอิน · เทสต์กระดานงานค้าง
ที่ยืนยันว่าไม่มีกราฟและไม่มีชื่อเจ้าหน้าที่ · เทสต์วันที่ที่ตรึงเวลาระบบ ·
เทสต์เอกสารรายคนและศูนย์สอบพิเศษเป็นแบบอย่างของการทดสอบอัปโหลดไฟล์ผ่านเบราว์เซอร์ ·
ตัวช่วยสร้างชื่อไม่ให้ชนกันระหว่างเทสต์ที่รันขนาน

**ไม่ทดสอบ** สคริปต์สร้างไฟล์นำเข้าสมมติ เป็นงานครั้งเดียว ตรวจด้วยจำนวนแถวและคำสั่ง
ตรวจความตรงของสถานะปัจจุบันแทน

## Out of Scope

- **กราฟและแผนภูมิทุกชนิด** รวมถึงรายงาน conversion — ยังอยู่ใน Out of Scope ของรอบแรก
  ด้วยเหตุผลเดิมคือรอให้ทีมใช้จริงก่อนจึงรู้ว่าอยากเห็นอะไร รอบนี้ทำตัวเลขล้วน
- **การวัดผลรายบุคคลของเจ้าหน้าที่** ทุกรูปแบบ (ADR-0004)
- **การกั้นข้อมูลระหว่างเจ้าหน้าที่** — เจ้าหน้าที่ทุกคนยังเห็นทุกอย่างเหมือนเดิม (ADR-0004)
  งานรอบนี้กั้นเฉพาะเส้นแบ่งเจ้าหน้าที่กับคนนอกทีม
- **ระบบเชิญและจัดการบัญชีในหน้าจอ** — รอบนี้ผูกบัญชีหัวหน้าทีมด้วยสคริปต์ `accounts:lead` (*เดิมเขียนว่า migration — เปลี่ยนในใบ 05 เพื่อไม่ให้อีเมลเข้า git*)
  และปิดการสมัครใหม่ด้วยมือบน Dashboard
- **การจำกัดโดเมนอีเมลของ Google** — ด่านคือการมีแถวเจ้าหน้าที่ ซึ่งแข็งกว่าและไม่พึ่งค่าที่
  Google อาจไม่ส่งมา
- **การเปิดสิทธิ์ให้คนนอกทีม** เช่น ผู้สนใจดูสถานะตัวเอง — ยังไม่มีหน้าสำหรับคนนอกทั้งระบบ
- **การจัดเวอร์ชันของเอกสารอ้างอิง** — อัปโหลดไฟล์ใหม่ทับได้ แต่ไม่เก็บประวัติเวอร์ชัน
- **การแยกฐานข้อมูลสำหรับชุดทดสอบ** — เป็นปัญหาจริงที่บันทึกไว้แล้ว แต่เป็นงานคนละก้อน
- **นำข้อมูลจริงกลับเข้าระบบ** — เขียนขั้นตอนไว้ให้ แต่เป็นการตัดสินใจของหัวหน้าทีมว่าจะทำเมื่อไหร่
- **ปีการศึกษาเป็นตัวกรองของกระดานภาพรวม** — รอให้รู้ก่อนว่าทีมนับปีการศึกษาเริ่มเดือนไหน
  ซึ่งยังไม่มีในคำศัพท์

## Further Notes

**ลำดับสำคัญ** ทำตามลำดับนี้เท่านั้น เพราะแต่ละขั้นลดความเสี่ยงของขั้นถัดไป

1. ปิดสิทธิ์เฉพาะเจ้าหน้าที่ — ลดความเสี่ยงทันที ไม่ต้องรออะไร
2. แทนข้อมูลจริงด้วยข้อมูลสมมติ — ทำหลังปิดสิทธิ์ เพื่อให้ระหว่างทำมีด่านกันอยู่แล้ว
3. จัดบัญชี ผูกบัญชี Google แล้วปิดการสมัครใหม่ — ทำหลังข้อมูลจริงออกไปแล้ว
4. เอกสารอ้างอิง
5. กระดานภาพรวมที่หน้าแรก

**ต้องสำรองไฟล์ข้อมูลจริงก่อนเริ่มข้อ 2** หลังล้างฐานข้อมูล ไฟล์นำเข้าต้นฉบับจะเป็นสำเนาเดียว
ของข้อมูลจริงที่เหลืออยู่ และมันอยู่ในโฟลเดอร์ดาวน์โหลดของเครื่องหัวหน้าทีมซึ่งมักถูกล้าง

**ADR ที่ต้องเขียน**

- **เฉพาะเจ้าหน้าที่จึงอ่านข้อมูลได้** — จำเป็นเพราะคนอ่านในอนาคตจะเห็น policy ที่รัดแล้วคิดว่า
  ขัด ADR-0004 ทั้งที่เป็นการรักษาเจตนาเดิมของ ADR นั้น ("คนนอกยังเข้าไม่ได้เลย")
  ที่ปุ่มลงชื่อเข้าใช้ด้วย Google ทำให้ไม่จริง ต้องอ้างอิงถึงกันสองทาง
- **เอกสารอ้างอิงอยู่นอกระบบเหตุการณ์** — จำเป็นเพราะ ADR-0001 บังคับว่าการเขียนข้อมูลคน
  ต้องผ่านเหตุการณ์ คนอ่านจะสงสัยว่าทำไมตารางนี้เขียนตรงได้

**ไม่ต้องเขียน ADR** สำหรับกระดานภาพรวมและการแทนข้อมูลด้วยของสมมติ — ย้อนกลับได้และเป็น
การตัดสินใจเชิงผลิตภัณฑ์ บันทึกใน spec และเอกสารความคืบหน้าพอ

**ของที่จะพังและต้องแก้ตามไปด้วย** เทสต์กระดานงานค้างที่ยืนยันว่าชื่อเจ้าหน้าที่จริงไม่โผล่ ·
ตารางแปลงชื่อผู้ดูแลตอนนำเข้าและเทสต์ของมัน · เอกสารออกแบบที่อ้างชื่อคนจริง ·
ตัวตั้งต้นการล็อกอินของชุดทดสอบ

**ตัวเลขที่ต้องแก้ในเอกสารความคืบหน้า** ระบุว่ามี migration 25 ไฟล์ (จริง 23) และ
เทสต์ผ่านเบราว์เซอร์ 70 รายการ (จริง 78) และข้อที่ติ๊กว่าสร้างบัญชีเจ้าหน้าที่ครบแล้ว
ควรระบุว่าเป็นบัญชีโดเมนสมมติ ไม่ใช่บัญชีจริงของทีม
