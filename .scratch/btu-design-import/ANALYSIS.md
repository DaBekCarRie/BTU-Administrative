## 1. ไฟล์ดีไซน์เป็นอะไร

เป็น **prototype เดียวจบ** ไม่ใช่ component library:

- HTML ก้อนเดียว + inline style ทุก element (ไม่มี CSS class เลย นอกจาก reset ใน `<helmet>`)
- ใช้ template DSL ของ Claude Design: `<sc-if value="{{ x }}">`, `<sc-for list="{{ xs }}" as="x">`, `{{ handler }}`
- logic อยู่ใน `class Component extends DCLogic` ท้ายไฟล์ — state ก้อนเดียว ~50 คีย์ (`screen`, `collapsed`, `openRow`, `docTab`, `detailTab`, `revealed`, …) ข้อมูลเป็น mock hard-code ทั้งหมด
- `support.js` คือ runtime ของ DSL — **ไม่ต้อง port**

**สรุป: ไฟล์นี้คือ spec ภาพ ไม่ใช่โค้ดที่ copy มาใช้ได้** ต้องอ่านแล้วแปลงเป็น React + Tailwind ตามของเดิมในโปรเจกต์

ดีไซน์ใช้สีจริงเพียงชุดเล็ก ๆ ควรทำเป็น CSS variable ก่อนแตะหน้าจอ:

| พื้นอวาตาร์ · แถวเน้นเบา | `#E8EEF5` · `#F7FAFD` |

| ตัวอักษร: หลัก / รอง / เงียบ / เงียบสุด | `#18181B` `#3F3F46` `#52525B` `#71717A` / `#A1A1AA` |
| แดง (เลยกำหนด / error) | ตัว `#B91C1C` `#991B1B` · พื้น `#FEE2E2` `#FEF2F2` · ขอบ `#FCA5A5` |
| เหลือง (รอดำเนินการ) | ตัว `#92400E` `#D97706` · พื้น `#FEF3C7` |
| เขียว (ผ่าน / สำเร็จ) | ตัว `#166534` `#15803D` · พื้น `#DCFCE7` `#F6FBF7` · ขอบ `#BBF7D0` |

- **ขนาดอักษร** 11 / 11.5 / 12 / 12.5 / 13 เป็นหลัก · หัวข้อหน้า 19 · ไม่มีอะไรเกิน 20
- **มุมโค้ง** 6px (ส่วนใหญ่) / 7 / 8 / 9 / 10px (การ์ด) / 999px (chip) / 50% (อวาตาร์)
- **focus ring** `border-color:#0F2A4A; box-shadow:0 0 0 3px rgba(15,42,74,0.10)`
- **ความสูงมาตรฐาน** input/ปุ่มในแถบกรอง 32px · ปุ่มในฟอร์ม 38–40px
- **ตัวเลขทุกตัว** ใช้ `IBM Plex Mono`
- `densityVars` → `--row-pad` สลับความสูงแถวตาราง 8px ↔ 12px (ของเดิมไม่มีสวิตช์นี้)

### ⚠ ดีไซน์นี้ไม่มีโหมดมืด

ทุกสีในไฟล์เป็น hex สว่าง ไม่มี `prefers-color-scheme` ไม่มีสีคู่ แต่โค้ดเดิมมี `dark:` **302 จุดใน 19 ไฟล์** — ต้องตัดสินใจก่อนเริ่ม (ดูข้อ 6)

## 4. ช่องว่างจริง แยกตามหน้า

### LOGIN — ต่างมากที่สุด เป็นงานชิ้นที่คุ้มสุด
ดีไซน์: พื้นหลังลายตาราง 56px, ตราสัญลักษณ์ BTU + ชื่อระบบด้านบน, **การ์ดขอบ `#E4E4E7` radius 10px padding 24px**, ปุ่ม Google มาก่อน → เส้นคั่น "หรือใช้อีเมลและรหัสผ่าน" → ฟอร์ม, กล่อง error แดงมีไอคอน, ท้ายหน้า "เข้าใช้ได้เฉพาะเจ้าหน้าที่ทีม LMS ที่ได้รับสิทธิ์แล้ว / ติดปัญหาการเข้าใช้ ติดต่อหัวหน้าทีม"
ของเดิม: `max-w-sm` เปล่า ๆ ไม่มีการ์ด ไม่มีตรา ไม่มีข้อความท้ายหน้า
→ **แก้แค่ชั้นนำเสนอ ไม่แตะ `actions.ts`**

### QUEUE — ใกล้แล้ว เหลือรายละเอียด
- ขาด: `section aria-label="กระดานงานค้าง"` — ของเดิมแสดงตัวเลข `board.*` อยู่ แต่ไม่ได้ทำเป็น grid ไทล์กดได้ `minmax(180px,1fr)` ที่มี label/value/hint
- ขาด: แถบสรุปในหัวหน้า (`summaryStrip`) และบรรทัด "ศุกร์ 12 กันยายน 2569 · อัปเดตล่าสุด 09:42 น."
- ขาด: คอลัมน์ "การกระทำ" แบบ sticky right (`position:sticky;right:0`) ในตารางกว้าง 1,020px
- มีแล้ว: ล้างตัวกรอง, บันทึกผลโทร, popover ในแถว, quick days, มือถือเป็นการ์ด + bottom sheet

### LEADS — ใกล้แล้ว
- มีแล้วทั้ง bulk bar (ส่งออกที่เลือก / เปลี่ยนผู้ดูแล / ยกเลิกการเลือก), paginate, chip สถานะบนมือถือ
- ขาด: ปุ่ม "ส่งออก CSV" ระดับหน้า (ของเดิมมี `export/route.ts` อยู่แล้ว — แค่ต่อปุ่ม)

### DOCUMENTS — ใกล้แล้ว
- ขาด: meta ของไฟล์ "ขนาดไฟล์" + "อัปโหลดเมื่อ" + ป้าย "พรีวิว" (`DeskDoc` ยังไม่เก็บขนาดไฟล์ → ดูข้อ 5)

### LEAD DETAIL — โครงต่างกันชัด
ดีไซน์แบ่ง 8 บล็อก: ข้อมูลติดต่อ · การศึกษาเดิมและหลักสูตร · เลขบัตรประชาชน · เอกสารประกอบ · **สถานะสามมิติ** (3 มิติ มีปุ่ม "ยืนยัน" ต่อมิติ) · บันทึกเหตุการณ์ (เลือกชนิด → แถว outcome/จำนวนเงินโผล่ตามชนิด) · ไทม์ไลน์เหตุการณ์ (เรียงใหม่→เก่า) + ปุ่มหัวหน้า ← ผู้สนใจ / ลงทะเบียนสมัคร / แก้ไขข้อมูล / ปิดเคส
ของเดิมแบ่งเป็น panel: applications / enrollment / exam / national-id / close / merge + หัวข้อ "สถานะ" "ข้อมูลติดต่อ"
→ **เป็นงานจัดเรียงใหม่ ไม่ใช่เขียนใหม่** ADR-0002 (สถานะสามมิติ) มีอยู่แล้ว ต้องเช็กว่าดีไซน์ตรงกับ ADR ไหม
มือถือ: ดีไซน์ใช้ **tab 2 อัน** (ข้อมูล / ไทม์ไลน์) — ของเดิมไม่มี

### LEAD NEW — จัดกลุ่มฟิลด์ใหม่
ดีไซน์: 3 fieldset (ข้อมูลผู้สนใจ / หลักสูตรที่สนใจ / ที่มาและบันทึกย่อ) + ปุ่ม "บันทึกและเปิดแฟ้ม" + เตือนเบอร์ซ้ำแบบ inline "เบอร์นี้มีอยู่แล้วในระบบ · <ชื่อ>" + หมายเหตุ "บันทึกนี้จะสร้างเหตุการณ์ 'ติดต่อเข้ามา' เป็นเหตุการณ์แรกของแฟ้ม"
ของเดิม `lead-form.tsx` มีฟิลด์ครบแต่ไม่ได้แบ่งกลุ่ม/ไม่มีเตือนซ้ำแบบนี้ (ต้องเช็กว่ามี duplicate check ฝั่ง server แล้วหรือยัง)

### EXAMS — เปลี่ยนมุมมอง
ดีไซน์: **ตารางคำขอ** 7 คอลัมน์ (ผู้สมัคร / หลักสูตร / ศูนย์สอบที่ขอ + จังหวัด / ผู้ขอร่วมศูนย์ / ยื่นเมื่อ / สถานะ / การกระทำ) + tab สถานะมี count + ปุ่ม "เพิ่มคำขอ" + คัดลอก**ข้อความแจ้งศูนย์สอบ** ต่อแถว + ถอนคำขอ
ของเดิม: จัดกลุ่มตามศูนย์ (`groupByCenter`) + ปุ่มคัดลอก**รายชื่อ**ต่อศูนย์
→ ต้องตัดสินใจว่าเอาแบบดีไซน์แทน หรือเพิ่มเป็นอีกมุมมอง

### FAQ — เปลี่ยนเป็น accordion
ดีไซน์: ช่องค้นหา + chip หมวด + accordion ต่อข้อ (คำถาม / "หมวด · ใช้ล่าสุด <วันที่>") กางแล้วเห็นคำตอบ + ปุ่ม "คัดลอกคำตอบ" / "แก้ไข" + empty state "ไม่พบคำตอบที่ตรงกับคำค้น / ลองใช้คำสั้นลง หรือเพิ่มคำตอบใหม่เข้าคลัง"
ของเดิม: list ธรรมดา ไม่มี accordion ไม่มี "ใช้ล่าสุด"

### MASTER DATA — สองบาน
ดีไซน์: ซ้ายรายการคณะ (11) กดเลือกได้ + ขวาตารางสาขาของคณะนั้น (ลำดับ / ชื่อสาขา / **ผู้สนใจที่เลือก** / สถานะ "เปิดรับ") + ปุ่ม "เพิ่ม" / "เพิ่มสาขา"
ของเดิม: ตารางเดียว คณะ→สาขาเป็น `<ul>` ไม่มีการเลือก ไม่มีจำนวนผู้สนใจ
→ **⚠ ปุ่มเพิ่มคณะ/สาขาขัดกับกฎเหล็กข้อ 1** (schema/ข้อมูลหลักแก้ผ่าน migration เท่านั้น) และขัดกับหมายเหตุในหน้าปัจจุบันที่เขียนไว้ตรง ๆ ว่า "ยังต้องแก้ผ่าน migration" — ดูข้อ 6

### ACCESS LOG — เพิ่มตัวกรองและคอลัมน์
ดีไซน์: คำโปรย "เห็นได้เฉพาะหัวหน้าทีม · ทุกครั้งที่มีการเปิดดูข้อมูลอ่อนไหวจะถูกบันทึกที่นี่ ลบไม่ได้" + ปุ่มส่งออก CSV + กรองตามเจ้าหน้าที่/ชนิดข้อมูล + ล้างตัวกรอง + "N รายการ · 30 วันล่าสุด" + ตาราง 6 คอลัมน์ (เวลา / เจ้าหน้าที่ / การกระทำ / **ชนิดข้อมูล** / แฟ้มที่เปิด / **ที่มา**)
ของเดิม: 4 คอลัมน์ (เมื่อไหร่ / ใคร / ทำอะไร / ของใคร) ไม่มีตัวกรอง

## 5. ช่องว่างชั้นข้อมูล (ต้องแก้ก่อน UI)

ดีไซน์แสดงของที่ยังไม่มีในฐานข้อมูล — ตรงนี้ต้องเป็น migration ไม่ใช่งานหน้าจอ:

| ดีไซน์ต้องการ | ของที่มี | ต้องทำ |
|---|---|---|
| access log: คอลัมน์ "ชนิดข้อมูล" + "ที่มา" | `AccessLogEntry { id, what, viewedAt, viewedByName, personName }` | เพิ่ม `kind` / `source` ใน `document_access_log` หรือ derive จาก `what` |
| access log: กรอง + 30 วันล่าสุด + ส่งออก CSV | `listAccessLog(limit=200)` เท่านั้น | เพิ่มพารามิเตอร์กรอง + route ส่งออก (ต้องมีด่านตรวจสิทธิ์ของตัวเอง — กฎข้อ 8) |
| master data: "ผู้สนใจที่เลือก" ต่อสาขา | `ProgramOption` ไม่มี count | aggregate จาก `people` |
| master data: สถานะ "เปิดรับ" | มี `is_active` อยู่แล้ว | แค่เปลี่ยนคำ |
| exams: จังหวัด / ผู้ขอร่วมศูนย์ / ยื่นเมื่อ | `ExamRequest { centerName, status, … }` | เพิ่ม `province`, `submitted_at`, นับกลุ่มต่อศูนย์ |

| documents: ขนาดไฟล์ | `DeskDoc` ไม่มี | อ่านจาก Storage metadata หรือเก็บตอนอัปโหลด |

## 6. เรื่องที่ต้องตัดสินใจก่อนลงมือ

1. **โหมดมืด** — ดีไซน์ไม่มี แต่โค้ดมี `dark:` 302 จุด
   เก็บไว้ (ต้องคิดสีคู่ให้ token ใหม่ทุกตัวเอง) / ถอดทิ้ง (งานรื้อ 19 ไฟล์) / คงไว้แบบไม่แตะ แล้วเพิ่ม token เฉพาะโหมดสว่าง
2. **หน้าที่ดีไซน์ไม่ครอบ** — `/` (หน้าแรก + funnel) และ `/reference` (เอกสารอ้างอิง, 441 บรรทัด) ไม่มีในดีไซน์ และเมนูในดีไซน์มีแค่ 5 รายการ (ของเดิม 7)
   ดีไซน์แค่ไม่ได้ครอบ ≠ สั่งให้ลบ — ต้องยืนยัน ไม่งั้นงานนี้จะทำเมนูหายสองอัน
3. **ปุ่มเพิ่มคณะ/สาขาในหน้าข้อมูลหลัก** ขัดกับกฎเหล็กข้อ 1
   ทำปุ่มแต่ disable + บอกว่าแก้ผ่าน migration / ข้ามปุ่มไป / เปิด ADR ใหม่ถ้าจะให้แก้ได้จริง
4. **exams เปลี่ยนมุมมอง** จากกลุ่มตามศูนย์ → ตารางคำขอ ทำให้ `groupByCenter()` และปุ่มคัดลอกรายชื่อต่อศูนย์ไม่มีที่ใช้ — แทนหรือเพิ่ม
5. **วันที่ในดีไซน์เป็น "12 กันยายน 2569"** → ต้องผ่าน `@/lib/date` ทั้งหมด ห้าม hard-code (กฎข้อ 5) และตัวเลขทั้งหมดในดีไซน์เป็น mock ห้าม copy
6. **`densityVars`** (สลับความสูงแถว) เป็นฟีเจอร์ใหม่ — เอาหรือไม่เอา

## 8. ผลกระทบต่อเทสต์

`e2e/` มี 20 spec ครอบทุกหน้าที่ดีไซน์แตะ และ **มี `home.spec.ts` กับ `reference.spec.ts` อยู่ด้วย**
→ ยืนยันว่าสองหน้าที่ดีไซน์ไม่ครอบเป็นของที่ทดสอบอยู่จริง ไม่ใช่ซากที่ลืมลบ (เสริมข้อตัดสินใจ 6.2)

selector ส่วนใหญ่ทนการจัดโครงใหม่: **`getByTestId` 284 จุด vs selector ที่อิงข้อความ 90 จุด**
spec ที่อิงข้อความมากสุดคือ `leads` (10) · `queue` (10) · `documents` (9) · `reference` (7)
→ สามหน้าแรกอยู่ในแผนทั้งหมด ต้องรันเทสต์หลังทุกขั้น ไม่ใช่รันครั้งเดียวตอนจบ

งานขั้น 13 (จัดโครง LEAD DETAIL ใหม่) กระทบ `applications` `enrollment` `national-id` `log-call` `duplicate` พร้อมกัน — อีกเหตุผลที่ควรทำท้ายสุด
