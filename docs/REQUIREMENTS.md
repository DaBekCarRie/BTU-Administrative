# Requirement — ระบบผู้สนใจ–ผู้เรียน BTU

สรุป ณ 11 ก.ย. 2569 · รวบรวมจากทุกเรื่องที่ตกลงกันมา
แยกชัดว่าอะไร **ยืนยันแล้ว** อะไร **ยังค้าง** เพื่อไม่ให้เข้าใจผิดว่าตกลงไปแล้ว

---

## 1. ที่มาของ requirement

วิเคราะห์จากของจริง 3 ชุด ไม่ใช่จากการสัมภาษณ์:

| แหล่ง | ปริมาณ | ใช้สรุปอะไร |
|---|---|---|
| `BTUบันทึกติดตาม(รายละเอียด).csv` | 3,180 แถว | โครงข้อมูลผู้สนใจ และปัญหาคุณภาพข้อมูล |
| ไฟล์ Excel 5 ชีท | 3 ปีการศึกษา | โครงใบสมัคร การเงิน เอกสาร |
| แชท LINE ธุรการ | 657 บรรทัด · 7 วัน | งานจริงประจำวัน และจุดที่ติดขัด |
| ภาพหน้าจอ | 35 ใบ | ขั้นตอนที่ทำผ่านแชทและรูปถ่าย |

## 2. ผู้ใช้

| บทบาท | จำนวน | ทำอะไร |
|---|---|---|
| เจ้าหน้าที่ (staff) | 5 คน | โทรตามผู้สนใจ บันทึกผล เก็บเอกสาร |
| หัวหน้าทีม (admin) | 1 คน | เห็นทุกอย่าง ดูรายงาน จัดการผู้ใช้ |

ทุกคนเป็นคนไทย ไม่ใช่สายเทคนิค · ทำงานบนมือถือเป็นหลักตอนโทร · อยู่ใน LINE ทั้งวัน

## 3. ขอบเขตรอบแรก — ยืนยันแล้ว

ผู้ใช้กำหนดมา 5 ข้อ:

1. **เก็บข้อมูลผู้สนใจ 3,180 ราย ให้ทีมใช้สะดวก**
2. **section สรุปคำถาม** — คลังคำถาม–คำตอบ
3. **เก็บเอกสารของผู้เรียนได้**
4. **login admin**
5. **CRUD ได้**

### ที่เพิ่มเข้ามาเพราะ 5 ข้อข้างบนใช้งานจริงไม่ได้ถ้าขาด

| # | requirement | เหตุผลจากข้อมูลจริง |
|---|---|---|
| 6 | หน้า **คิวโทรวันนี้** | CRUD บอกไม่ได้ว่าวันนี้ต้องทำอะไร — นี่คือ "ความสะดวก" ในข้อ 1 |
| 7 | ประวัติติดตามเป็น**แถว ไม่จำกัดจำนวน** | ของเดิมเป็น 6 คอลัมน์ และมี 42 คนใช้ครบแล้ว เพดานชนจริง |
| 8 | แยก **สถานะ** ออกจาก **วันที่นัดโทร** | 1,486 จาก 1,530 แถวในช่องวันที่ไม่ใช่วันที่ แต่เป็นสถานะ |
| 9 | **dropdown** ทุกช่องประเภท | คณะ 10 คณะกลายเป็น 64 ค่า · แอดมิน 5 คนกลายเป็น 16 ค่า |
| 10 | **กันข้อมูลซ้ำ** + ปุ่มรวมเป็นคนเดียว | ชื่อซ้ำ 122 แถว · เบอร์ซ้ำ 16 แถว |
| 11 | **สคริปต์ import + ล้างข้อมูล** มี dry-run | ถ้าเปิดระบบมาว่างเปล่า ทีมกลับไปใช้ชีทภายในวันเดียว |
| 12 | **audit log** ว่าใครแก้อะไร | 5 คนแก้ข้อมูลชุดเดียวกัน |
| 13 | **login + RLS ทุกตาราง** | เจ้าหน้าที่ทุกคนเห็นข้อมูลทั้งหมด (ดู ADR-0004) แต่คนนอกเข้าไม่ได้เลย |

### requirement ที่ควรมี (ไม่ใช่ต้องมี)

14. ค้นหาพิมพ์ไม่ครบก็เจอ — รองรับชื่อไทยและอังกฤษปนกัน
15. ใช้บนมือถือได้ · เบอร์เป็นลิงก์กดโทร
16. บันทึกย้อนหลังได้ (โทรแล้วมาบันทึกทีหลัง)
17. ส่งออก Excel
18. แจ้งเตือนเข้ากลุ่ม LINE ตอนเช้า

### เรื่องเอกสาร (ข้อ 3) — ขาดไม่ได้ถ้าจะเก็บเอกสารจริง

19. **Private bucket + signed URL หมดอายุ** — ในนั้นมีบัตรประชาชน
20. **บันทึกทุกครั้งที่มีคนเปิดดู**
21. **เช็กลิสต์ 4 ประเภท + สถานะตรวจ** (รูปถ่าย · วุฒิ · สำเนาบัตร · สำเนาทะเบียนบ้าน)
    สถานะ: ยังไม่ส่ง / ส่งแล้ว / ผ่าน / ไม่ผ่าน + เหตุผลถ้าไม่ผ่าน
22. **บันทึกการยินยอม PDPA**

## 4. requirement เชิงข้อมูล

จากการวิเคราะห์ไฟล์จริง — ตัวเลขเหล่านี้คือเกณฑ์ที่ระบบต้องรับมือได้:

```
ผู้สนใจเริ่มต้น        3,180 ราย   (โตประมาณ 500/ปี)
บันทึกติดตาม           1,204 รายการ (สูงสุด 6 ครั้ง/คน — ต้องรองรับมากกว่านี้)
มีเบอร์โทร               19%        (ที่เหลือติดต่อทาง Facebook/Line เท่านั้น)
มี Facebook              90%
คณะที่ต้อง normalize   64 → 10
สาขา                    90 → ~25
วุฒิ                    43 → 5
ชื่อแอดมิน              16 → 5
วันที่เก็บเป็น text    31% ของทั้งหมด
```

### กฎข้อมูลที่ระบบต้องบังคับ

- ปีการศึกษาเป็น **ช่องข้อมูล** ไม่ใช่ตารางหรือไฟล์แยก (ของเดิมแยกชีทต่อปี คอลัมน์ไม่ตรงกัน 42 vs 36)
- วันที่เก็บเป็น **ค.ศ. (`timestamptz`)** เสมอ แปลงเป็น พ.ศ. ตอนแสดงผลเท่านั้น
- เบอร์โทรผ่าน `normalizePhone()` ก่อนบันทึกเสมอ
- เลขบัตรประชาชนเก็บ**เข้ารหัส** แสดงแค่ 4 ตัวท้าย

---

## 5. requirement เชิงความปลอดภัย

1. RLS เปิดทุกตาราง ไม่มีข้อยกเว้น
2. เลขบัตรประชาชนเข้ารหัสด้วย `pgcrypto` คีย์อยู่ใน Supabase Vault
3. ถอดรหัสผ่าน function `security definer` ที่เช็ค role แล้วเขียน `audit_log` ทุกครั้ง
4. Storage bucket private ทั้งหมด เข้าถึงผ่าน signed URL อายุสั้น
5. `SUPABASE_SERVICE_ROLE_KEY` ห้ามปรากฏใน Client Component
6. **ต้องทดสอบด้วยมือ**: ยืนยันว่าคนที่ยังไม่ล็อกอินเรียก API ตรง ๆ แล้วไม่ได้ข้อมูลเลย

ข้อ 6 สำคัญที่สุด เพราะ AI มักเขียน RLS policy ที่ดูถูกแต่เปิดกว้างเกินจริง
ในระบบนี้เจ้าหน้าที่เห็นกันหมดโดยตั้งใจ (ADR-0004) แต่ **คนนอกต้องไม่เห็นอะไรเลย**
ซึ่งเป็นเส้นที่ห้ามพลาด

## 7. ตัดสินแล้วจากการ grill (11 ก.ย. 2569)

ทุกข้อที่เคยค้างถูกปิดหมดแล้ว บันทึกเหตุผลไว้ใน ADR ที่อ้างถึง

| เรื่อง | ผล | ที่มา |
|---|---|---|
| โครงข้อมูล | เหตุการณ์เพิ่มอย่างเดียว + สถานะปัจจุบันที่คำนวณไว้แล้ว | [ADR-0001](adr/0001-hybrid-event-log.md) |
| สถานะ | แยก 3 มิติ ติดตาม / การเรียน / การเงิน | [ADR-0002](adr/0002-three-status-dimensions.md) |
| แหล่งความจริง | ระบบนี้เก็บสำเนา ไม่ใช่เจ้าของ — ต้องแสดงวันที่ยืนยันล่าสุดเสมอ | [ADR-0003](adr/0003-not-the-source-of-truth.md) |
| สิทธิ์เข้าถึง | เจ้าหน้าที่เห็นหมด ไม่กั้นตามเจ้าของเคส | [ADR-0004](adr/0004-no-access-partitioning.md) |
| เอกสาร | เอกสารประจำตัวผูกกับคน ใช้ซ้ำข้ามการสมัครได้ · เอกสารธุรกรรมแนบกับเหตุการณ์ | รอบ 3 |
| ขอบเขตปลายทาง | มีช่องสถานะการเรียนให้บันทึกเมื่อรู้ ระบบไม่ไล่ตามเอง | รอบ 3 |
| ชุดเหตุการณ์ | 14 ชนิด ยังไม่รวม กยศ. (ข้อมูลเดิมกรอกแค่ 14%) | รอบ 3 |
| สรุปคำถาม | คลังเดียว + ป้าย "ตอบผู้สนใจได้ / ใช้ภายใน" + ยืนยันล่าสุดโดยใคร | รอบ 3 |
| หน้าสมัครสาธารณะ | ไม่อยู่รอบแรก — ผู้สนใจ 90% มาทาง Facebook ไม่ใช่ฟอร์ม | รอบ 3 |
| dashboard | กระดานงานค้างเป็นหน้าแรก + แถบตัวเลขรวม ไม่มีตัวเลขรายบุคคล | รอบ 2 |
| ศูนย์สอบ | เก็บแค่คำขอศูนย์สอบพิเศษ ไม่แตะการลงทะเบียนสอบของมหาวิทยาลัย | รอบ 2 |
| วัดผลทีม | ไม่ทำ | รอบ 1 |

คำศัพท์ทั้งหมดอยู่ใน [CONTEXT.md](../CONTEXT.md)

## 8. สถานะงาน ณ ตอนนี้

### เสร็จแล้ว

- วิเคราะห์ข้อมูลครบทั้ง 3 ชุด
- ออกแบบสถาปัตยกรรม 14 โมดูล (ดู artifact "สายพานนักศึกษา BTU")
- เลือก stack ครบทุกชั้น → `docs/STACK.md`
- prompt ออกแบบหน้าจอ 7 หน้า → `docs/PROMPT-design.md`
- วางโครงโปรเจกต์: Next.js 16 + Supabase (`btu-admin`, ap-southeast-1) +
  shadcn/ui + client 3 ตัว + proxy กันเส้นทาง + ยูทิลิตี้ พ.ศ./เบอร์โทร/LINE
- build ผ่าน · typecheck ผ่าน · เชื่อมฐานข้อมูลได้จริง · ไม่มี security advisor เตือน

### ยังไม่ได้ทำ

- **ยังไม่มีตารางในฐานข้อมูลเลย** (มีแค่ extension `pgcrypto` + `pg_trgm`)
- ยังไม่ได้ออกแบบหน้าจอ (ยังไม่ได้รัน `/design`)
- ยังไม่ได้ implement ฟีเจอร์ใด ๆ
- `SUPABASE_SERVICE_ROLE_KEY` ใน `.env.local` ยังว่าง — ต้องก๊อปจาก Dashboard เอง

## 9. เกณฑ์ว่ารอบแรกสำเร็จ

ไม่ใช่ "โค้ดเสร็จ" แต่คือ:

1. ทีมเปิดระบบตอนเช้าแล้วรู้ทันทีว่าวันนี้ต้องโทรหาใคร
2. บันทึกผลโทรจากมือถือจบได้ใน 3 แตะ
3. ไม่มีช่องไหนที่พิมพ์ชื่อคณะ/สาขา/วุฒิ/แอดมินเป็นข้อความอิสระได้
4. ข้อมูลเดิม 3,180 แถวอยู่ในระบบครบ
5. **ผ่านไป 2 สัปดาห์แล้วทีมยังไม่กลับไปเปิด Google Sheets**

ข้อ 5 คือเกณฑ์จริงข้อเดียว
